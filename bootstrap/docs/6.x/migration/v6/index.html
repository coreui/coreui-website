Migrating to v6

MarkdownChatGPTClaude

Track and review changes to the CoreUI for Bootstrap source files, documentation, and components to help you migrate from v5 to v6.

On this page
  • v6.0.0 (unreleased)
  • Dependencies
  • Distributed files
  • Browser support
  • JavaScript
  • Components
  • Helpers
  • Sass architecture & design tokens
  • Sass & CSS

Work in progress. v6 is under active development on the v6-dev branch — this page tracks every migration-relevant change as it lands, so nothing here is final until a v6 release ships. The class API keeps its meaning — .btn-primary, .alert-success and friends render as before. Where the Sass or CSS-variable surface does change, the entry below carries a Breaking badge.

v6.0.0 (unreleased)

Dependencies

  • Popper is gone; @floating-ui/dom replaces it. Breaking Every positioned component — tooltips, popovers, dropdowns, autocomplete, multi-select, and the pickers — now positions with Floating UI. @popperjs/core is no longer a peer dependency and the bundle builds (coreui.bundle.*) no longer include it. What to change:
    • npm: replace @popperjs/core with @floating-ui/dom in your dependencies.
    • CDN (non-bundle builds): replace the popper.min.js script tag with the two Floating UI files, in this order: floating-ui.core.umd.min.js, then floating-ui.dom.umd.min.js.
    • The popperConfig option (tooltip, popover, dropdown) is now floatingConfig and receives a Floating UI computePosition config — Popper’s modifiers array does not translate; use Floating UI middleware.
    • The tip and menu carry data-coreui-placement instead of Popper’s data-popper-placement; CSS or JS keying on the old attribute needs the new name.
    • Positioning is now asynchronous (computePosition is promise-based). Code that read the tip’s coordinates synchronously right after show() should wait for the shown event.

Distributed files

  • The *.rtl.css builds are gone. Breaking One stylesheet now serves both directions, so dist/css no longer carries coreui.rtl.css, coreui-grid.rtl.css, coreui-reboot.rtl.css, coreui-utilities.rtl.css, their minified twins, source maps or SRI hashes — 20 files in all. Everything positional was already written with logical properties; the six places that genuinely differ (the off-canvas panel, the range slider’s label and tooltip, the select and validation arrows, the carousel controls, the breadcrumb divider) now emit their mirrored declaration from a :dir(rtl) rule in the same file, matched on the element’s own direction rather than on an ancestor. That costs about 500 bytes gzip, where an RTL reader used to download a second 56 kB stylesheet.

    What to change: drop the .rtl from your stylesheet link and keep dir="rtl" on <html>. $enable-rtl: false still produces an LTR-only build and $enable-ltr: false an RTL-only one, so nothing that was possible before stops being possible.

  • The Bootstrap theme and the Bootstrap-compatible JavaScript are gone. Breaking dist/css/themes/bootstrap/bootstrap.css, dist/js/bootstrap.js, bootstrap.bundle.js and bootstrap.esm.js no longer ship, with their minified twins, source maps and SRI hashes, and neither does scss/themes/bootstrap/bootstrap.scss. The two halves no longer agreed in v6: the JavaScript wrote data-bs-* attributes and --bs-* properties where the stylesheet still read data-coreui-* and --cui-* ones.

    What to change: load coreui.min.css and coreui.bundle.min.js (or coreui.min.js), write data-coreui-* attributes, listen for *.coreui.* events, reach the plugins through coreui instead of bootstrap, and set --cui-* properties instead of --bs-*.

  • dist/css gained base.css and a stylesheet per component. base.css holds the :root tokens and Reboot; css/components/ holds one file per component plus manifest.json, which records each file’s load order and the components it needs alongside it. Nothing was taken away — coreui.css still carries everything — so this is additive, and pages that use a few components can now ship a few kilobytes of CSS instead of the whole library. See per-component CSS files.

  • dist/css gained coreui-legacy.css, and coreui.css lost the v5 spellings it carries. Breaking coreui.css is the v6 class API only. The deprecated v5 spellings — the colour modifiers (.alert-{color}, .btn-{color}, .btn-outline-{color}, .btn-subtle-{color}, .btn-ghost-{color}, .callout-{color}, .chip-{color}, .list-group-item-{color}), the form check markup (.form-check, .form-check-input, .form-check-label, .form-check-inline, .form-switch, .form-switch-lg / -xl) and .btn-check on the input — moved to coreui-legacy.css, 3.4 kB gzip. That takes 2.1 kB gzip off coreui.css for markup that has already moved, and turns the compatibility layer into something you can see on a network tab and delete in one line.

    What to change: if your markup still uses any of them, add the sheet after coreui.css (or last, after base.css and the component files):

    <link href="css/coreui.min.css" rel="stylesheet">
<link href="css/coreui-legacy.min.css" rel="stylesheet">

    From Sass, @use "coreui-legacy"; next to your @use "coreui";. Everything in it is still removed in v7. See v5 compatibility CSS.

  • $enable-deprecated-classes and $enable-deprecated-form-check are gone. Breaking A separate stylesheet answers the question both flags existed for, without a recompile: false is now “do not load coreui-legacy.css”. Sass builds that set either flag fail with an unknown-variable error — delete the line.

Browser support

Breaking

The minimum supported browsers are now Chrome 123, Edge 123, Firefox 129, Safari 18 and iOS 18. Safari 18 is set by color-mix(): a mix in oklch with an achromatic operand — transparent, white, black, the greys, which is how every translucent and tinted colour in v6 is made — keeps the other colour’s hue only from Safari 18, where WebKit started carrying missing components forward as the spec requires; Safari 17.x interpolates the hue towards 0° and renders indigo as pink. Apple ships Safari 18 for macOS 13 and 14 as well, so the cut only affects browsers left un-updated. light-dark() sets the Chrome/Edge floor; @starting-style and transition-behavior: allow-discrete set Firefox 129 (the Menu’s entry animation) and @property needs 128 — its inherits: false registrations are what stop the colour and opacity utilities leaking into descendants, so an older Firefox does not lose an animation, it gets a bug. :has() sets a lower bound of Firefox 121, since validation and focus states on Multi Select, Autocomplete and the pickers, the sidebar navigation indicators, calendar ranges and the rating icons are all selected with it — and an unsupported :has() invalidates the entire rule it appears in. This is the floor the v6 color system already required in practice: theme decisions resolve in the browser via light-dark() and color-mix() with no fallback, so on older browsers dark mode did not work regardless of what the previous .browserslistrc claimed (Chrome 60 / Safari 12). v6 makes the declaration honest and takes the wins: the compiled CSS drops legacy vendor prefixes (about 8 kB gzip off coreui.min.css) and the JavaScript ships modern syntax un-transpiled. If you must support older browsers, stay on v5.

JavaScript

v6’s JavaScript is written in TypeScript. The published behaviour is unchanged — the sources were converted module by module against a gate that required the minified bundles to stay byte-identical — but the package now carries types, and what it ships from js/ has changed.

Type declarations ship with the package

@coreui/coreui-pro now ships .d.ts files and points types at js/dist/index.d.ts, so TypeScript consumers get the full API without @types packages or hand-written module declarations:

import { Modal, MultiSelect } from '@coreui/coreui-pro'

const modal = new Modal('#example', { backdrop: 'static', keyboard: false })
const version: string = Modal.VERSION

Each component with options also exports its config type (ContextMenu and Dropdown take Menu’s MenuConfig), so an options object can be typed and reused, and takes it in the constructor and getOrCreateInstance, so an option it does not know is a type error; a picker also takes the options it forwards to its calendar, its field and its time columns, except those it sets itself. Declarations are generated from the sources, not maintained by hand, and CI type-checks a consumer file against the emitted declarations, so the shipped types cannot drift from the code.

The js/src sources ship as TypeScript

Breaking

The package used to ship js/src/**/*.js; it now ships js/src/**/*.ts. The documented per-plugin path is unaffected — js/dist/*.js still ships, UMD-ready, and that is what the Webpack, Vite and Parcel guides tell you to import:

import Alert from '@coreui/coreui-pro/js/dist/alert'

A bundler that reads the package’s exports now resolves that import to the ES module next to the UMD file, js/dist/alert.mjs; a require() still gets js/dist/alert.js.

Only imports that reached into the raw sources are affected:

- import Alert from '@coreui/coreui-pro/js/src/alert.js'
+ import Alert from '@coreui/coreui-pro/js/dist/alert.js'

If your toolchain compiles TypeScript, you can import js/src/*.ts directly and get types and tree-shaking together. The per-plugin files are typed as well — js/dist/alert.js ships next to js/dist/alert.d.ts, and js/dist/alert.mjs next to js/dist/alert.d.mts.

js/index.esm.js and js/index.umd.js are no longer published

Breaking

These two files are the bundler’s entry points, and they import the sources — which are now TypeScript, so the files could not resolve for a consumer anyway. They are no longer part of the published package. Use the built bundle instead:

- import { Tooltip } from '@coreui/coreui-pro/js/index.esm.js'
+ import { Tooltip } from '@coreui/coreui-pro/dist/js/coreui.esm.js'

or, if you are already resolving the package by name, import { Tooltip } from '@coreui/coreui-pro' — module points at the same ESM bundle.

Unused date helpers are gone from js/dist/util

Breaking

The util modules are internal, but the package exports every file under js/dist, so a deep import could reach them. These helpers are no longer exported: js/dist/util/date-range-picker.js as a whole, getFirstAvailableDateInRange, getSelectableDates, createDateFromMonth, createDateFromWeek and createDateFromYear from util/calendar.js, getDateSections from util/date-sections.js (now getSectionLayout), and convertTimeToDate, formatTimePartials, getAmPm, isValidTime and shouldUseTwoDigitHour from util/time.js. Most had no reader in the library and are gone; createDateFromYear, formatTimePartials and shouldUseTwoDigitHour stay as module internals. Pass dates to the components in the formats their options take (startDate: '2026W03' with selectionType: 'week'), or keep a copy of the helper in your code. The nine per-unit comparisons of util/calendar.js, isMonthDisabled, isMonthInRange, isMonthSelected and their isQuarter… and isYear… counterparts, are three functions that take the calendar view as the second argument: isPeriodDisabled(date, 'months', min, max, disabledDates), isPeriodInRange(date, 'quarters', start, end) and isPeriodSelected(date, 'years', start, end).

CalendarUtil and RangeUtil in the per-file UMD builds

Loaded with a plain <script>, js/dist/util/calendar.js registers as CalendarUtil, and the new js/dist/util/range.js as RangeUtil. The calendar util used the Calendar global of the component, so the two files overwrote each other and js/dist/calendar.js read its helpers from itself. Load the util file before the component, as with the other js/dist/util files.

coreui.Offcanvas in the UMD bundle

The UMD bundle exposed the offcanvas plugin as coreui.OffCanvas, while the ESM bundle, the per-plugin file and the docs all call it Offcanvas. The UMD global now carries coreui.Offcanvas as well; coreui.OffCanvas stays as an alias of the same class, so existing scripts keep working:

- const offcanvas = new coreui.OffCanvas('#offcanvasExample')
+ const offcanvas = new coreui.Offcanvas('#offcanvasExample')

The UMD bundle keeps what companion packages put on window.coreui

coreui.js and coreui.bundle.js used to replace window.coreui with a fresh object, so coreui.Utils, coreui.ChartJS, coreui.DataGrid or coreui.Scheduler loaded before the library were gone once it loaded. The library now copies the entries of an existing plain window.coreui into its own object, so the order of the script tags no longer matters. Anything else under that name, such as an element with id="coreui", is still replaced.

One jQuery dispatcher for every plugin

Every $(el).plugin('method') call now goes through the same dispatcher: the instance is created or reused, a string argument names a public method, and anything else throws TypeError: No method named "…". A few plugins used to let a private name through ($(el).tooltip('_getConfig') called it) or skipped the check altogether (button, number-input, password-input); they now reject those names like the rest.

The attribute that enables a plugin

data-coreui-toggle="…" now means one thing only: this element is a control the user activates. It stays on the <button>, <a> or <input> that opens, closes or presses something — Modal, Offcanvas, Dialog, Drawer, Collapse, Tab, Tooltip, Popover, Context Menu, Combobox, Button, Loading Button.

Everywhere else the element is a mount point or a source: the plugin builds the component inside or around it, and nothing is toggled. Those take a bare data-coreui-<name>, the shape Chip Input, Chip Set, Multi Select and the masked date and time fields already used. Renamed:

- <div data-coreui-toggle="date-picker"></div>
+ <div data-coreui-date-picker></div>

Lifecycle methods return a promise

show(), hide(), toggle() and close() returned before the transition ended, so continuing after one meant listening for shown.coreui.* / hidden.coreui.*. They now return a promise that resolves at the same moment that event fires, so you can await the method instead:

- myCollapseEl.addEventListener('shown.coreui.collapse', () => {
-   // the area is expanded
- })
- collapse.show()
+ await collapse.show()
+ // the area is expanded

Collapse, Menu, Modal, Offcanvas, Popover, Sidebar and Tooltip return one from show/hide/toggle, Toast from show/hide, Tab from show, and Alert from close. The event path is unchanged and still the right tool when you must react to changes your own code did not start.

The promise always settles — a call that does nothing (already open, a prevented show.coreui.*, an instance disposed mid-transition) resolves right away rather than stranding the caller. It resolves with no value, so it tells you the call finished, not whether the state changed.

Live changes go through setters, not update(config)

Breaking

update() meant two different things. On Combobox, List box, Transfer, Menu, Progress, Range, Tooltip and Popup it takes no argument and recomputes from what the component already owns; on Autocomplete, Calendar, MultiSelect, OTP Input, Range Slider, Rating and the date/time inputs it took an options object and replaced the configuration. Calling it the first way on a component that meant the second one threw a TypeError.

Options are now fixed once a component starts. What can change on a live instance, its value, its data and its state, has a method of its own, named after the option it changes:

- multiSelect.update({ options })
+ multiSelect.setOptions(options)
- rating.update({ value: 2 })
+ rating.setValue(2)
- dateInput.update({ validationState: 'invalid' })
+ dateInput.setValidationState('invalid')
- autocomplete.update({ disabled: true })
+ autocomplete.disable()

  • The date and time setters fire no change event, since the code that calls them already holds the value. setDate() of Date Input, Time Input and Date Picker, setTime() of Time Picker, setStartDate(), setEndDate() and setRange() of Date Range Input, Date Range Picker and Calendar, and setCalendarDate() and setSelectEndDate() of Calendar change the value without dateChange, timeChange, startDateChange, endDateChange, calendarDateChange, selectEndChange or the native input and change of the value field; errorChange still reports a date the field refuses.   • Other options are fixed. A new format, size, label, icon, name, required or readonly means disposing the instance and creating a new one. update() applied some of them, such as format on Date Input or size on Rating, and ignored the rest in silence on Combobox, Chip Input, Date Range Input and the pickers.
  • A setter keeps what it does not set. setValue() keeps a given validation state, setValidationState() keeps the value, and Rating and Range Slider no longer fall back to the defaults: rating.setValue(2) on a rating built with { itemCount: 3 } keeps three items.
  • The setters are reachable the same way everywhere, including through the static and jQuery dispatchers, which pass the method name and whatever follows it: coreui.Rating.ratingInterface(el, 'setValue', 2).

Toaster.update(id, options) is unchanged — it rewrites one toast in the store rather than reconfiguring the component.

A getter says what it returns

Breaking

getSelected() returned three different things. List box gave the selected values, Chip Set gave the selected elements while getSelectedValues() sat next to it giving the values, and Transfer required an argument no other component takes:

chipSet.getSelected().join(',') // [object HTMLDivElement],[object HTMLDivElement]
transfer.getSelected()          // TypeError: Cannot read properties of undefined

Every getter now carries the noun it returns:

- listBox.getSelected()
+ listBox.getSelectedValues()

- chipSet.getSelected()
+ chipSet.getSelectedValues()

- transfer.getSelected('source')
+ transfer.getSelectedValues('source')

Chip Set’s getValues() and getSelectedValues() are unchanged and are now the whole selection API: the element list behind them is internal. A chip carries a value of its own — data-coreui-chip-value, falling back to the chip’s text — so values, not nodes, are what the rest of the plugin works with.

Transfer still takes 'source' or 'target', the argument its setLoading(loading, list) already takes. Anything else now throws a TypeError naming the two lists instead of failing on an undefined property.

The “N selected” text is one option, and it can be a function

Breaking

Four components rendered the same sentence under three option names and two shapes: Combobox substituted {count} into selectedText, List box and Transfer appended selectedCounterText after count/total, and Multi Select appended selectionTypeCounterText after the count.

Appending cannot be translated. A translator receives only the tail of the sentence, so the number cannot move and the noun cannot be inflected — Polish needs “2 zaznaczone”, “5 zaznaczonych” and “1 zaznaczony” from the same option, and a language that puts the number last cannot be served at all.

- new coreui.MultiSelect(el, { selectionTypeCounterText: 'item(s) selected' })

One selection event, one payload key

Breaking

event.value carries what that component’s own getter returns, which is the one thing the key never told you before: getValue() for Autocomplete and Combobox, the selected values for List box (an array even in single mode), the selected options for Multi Select, the chip values for Chip Set and Chip Input. Two events keep their own names because they answer a different question. select.coreui.chip-set still carries selected — membership and selection are separate in a chip set — and move/moved.coreui.transfer still carry direction and the values that are moving, which is the change itself rather than the state after it.

On a page that loads jQuery, the two renamed events now reach onchange handlers written as a DOM property or an inline attribute, on the element or any ancestor: jQuery’s own trigger drops the namespace for that one path. Measured in Chromium, a document.onchange handler goes from zero calls to one per selected option. The five components that already fired change have always behaved this way. Handlers bound with $(el).on('change') are not affected, and neither is addEventListener.

changed.coreui.range keeps its name. It is not a selection event: Range relays the value of the native <input type="range"> it decorates, on every native input and change. Range Slider, the component of this family that does have a selection, already fires change.

announce() (new)

announce(message, { context, priority, timeout }) reads a message to screen reader users through a visually hidden live region of the page, or of the open modal dialog, native or marked with aria-modal="true" like the panel of a date picker, since a modal dialog leaves the rest of the page inert. priority takes the values of ariaNotify(), 'normal' and 'high'. Toaster announces its toasts through it. See Accessibility.

Components

Accordion on the native <details>

  • Breaking The accordion renders on the native <details>/<summary> elements now. .accordion-item goes on a <details> element and .accordion-header on its <summary>; the browser opens and closes the panel, so the component needs no initialization and works on markup added after load.

  • Breaking .accordion-button, .accordion-collapse and .collapsed are gone. The trigger is the <summary> itself and the panel is the element’s own content, revealed through ::details-content. Style the open state with .accordion-item[open] > .accordion-header instead of :not(.collapsed).

  • Breaking Grouping moves from data-coreui-parent to the name attribute. Give the <details> elements of one accordion the same name to keep a single item open at a time; omit it for an always-open accordion. The id plumbing (data-coreui-target, aria-controls, aria-expanded) is no longer needed — the browser exposes the disclosure state on its own.

  • A <summary> is not a heading. Where the accordion divides a page into sections, wrap the label in an <h2>–<h6> inside the summary; the heading inherits the summary’s typography.

  • The header’s focus ring draws 1px inside the item (--cui-focus-ring-offset: -1px on .accordion-header:focus-visible), so it no longer overlaps the borders of adjacent items.

  • The panel animation is CSS-driven through interpolate-size: allow-keywords, which only Chromium implements today. accordion.js supplies the same animation in Firefox and Safari; that part of it goes away, without a breaking change, once they ship calc-size(). The component’s events and methods do not depend on it and stay either way.

  • Breaking The accordion’s events replace Collapse’s. shown/hidden.coreui.accordion fire on the .accordion-item whenever its open state changes, mirroring the native toggle event but bubbling, so they can be delegated. There is no show/hide counterpart: <details> has no cancelable event before the state change, so an item is kept shut by cancelling the click on its <summary> instead of by preventing an event.

  • Breaking The plugin replaces Collapse’s, and it is instantiated on the .accordion container, not on a panel. Where v5 called Collapse.getOrCreateInstance(panel).show(), v6 calls Accordion.getOrCreateInstance(accordion).show(item), with the item given as an element or as its index. hide() and toggle() take the same argument, and showAll() / hideAll() open and close the whole accordion — the latter pair also handles the name juggling the HTML Standard requires, which is why expanding an exclusive accordion is a plugin call rather than a loop over open. None of it is needed to open and close items; the element does that on its own.

  • The header draws its focus ring on :focus-visible, not :focus. A mouse click no longer paints a ring, keyboard focus still does, matching .btn.

  • New CSS variables: --cui-accordion-active-border-color (the open item’s border and the header’s inset shadow, previously stuck on the resting border colour), plus --cui-accordion-content-duration and --cui-accordion-content-easing, which drive the panel transition and are read back by accordion.js so both paths animate for the same length of time.

  • The indicator can be an element instead of a background image. Put an <svg class="accordion-icon"> in the <summary> and the header stops drawing its own icon, so any icon set or <img> can be used without URL escaping an SVG into a custom property. --cui-accordion-header-active-icon selects the shape shown while the item is open, and a second element marked .accordion-icon-active does the same in markup — that is what a plus/minus accordion needs, where the icon is swapped rather than rotated. The default chevron and its rotation are unchanged when neither is used.

  • Breaking The open item is neutral, and .theme-{color} is what tints it. --cui-accordion-active-bg and --cui-accordion-active-color were fixed to --cui-primary-bg-subtle / --cui-primary-fg-emphasis, so every accordion turned the brand colour on open whether or not that suited the page. They are --cui-bg-2 and --cui-fg-body now, and the active tokens resolve through --cui-theme-fg / -bg-subtle / -border first — so the colour is a decision you make per accordion instead of one baked into the component. To keep the old look, put .theme-primary on the .accordion.

  • Breaking --cui-accordion-inner-border-radius is gone; the header’s corners follow --cui-accordion-border-radius. The token was computed from the global --cui-border-radius when the stylesheet was built, so setting --cui-accordion-border-radius rounded the item while the header inside kept the page’s default radius. The two corners are subtracted where they are used — calc(var(--cui-accordion-border-radius) - var(--cui-accordion-border-width)) — so one token now shapes the whole item. Defaults render as before; drop any override of the removed variable.

  • Breaking The header tokens are named after the header. The summary is not a button any more, so --cui-accordion-btn-* is --cui-accordion-header-* (-color, -bg, -icon, -active-icon, -icon-width, -icon-color, -active-icon-color, -icon-transform, -icon-transition) and the $accordion-header-* Sass variables are $accordion-header-*. Rename in place; nothing else about them changed.

  • One padding token and one font size for the whole control. --cui-accordion-padding-x / -y and --cui-accordion-font-size are read by the header and the body alike, so resizing an accordion is one declaration instead of four. --cui-accordion-header-padding-* (was -btn-padding-*) and --cui-accordion-body-padding-* are still there for resizing one part, declared on .accordion as var(--cui-accordion-padding-*). Because they resolve where they are declared, override --cui-accordion-padding-* on .accordion (or a .accordion-* size class), not on a single .accordion-item — there it no longer reaches the header and the body.

Breadcrumb

  • Breaking The breadcrumb has no bottom margin. .breadcrumb sat on margin-bottom: 1rem through $breadcrumb-margin-bottom and --cui-breadcrumb-margin-bottom; both are gone and the list ends where its content ends, like every other navigation component. Add .mb-5 (or set margin-bottom on the <nav>) where the page relied on that gap.
  • Three breadcrumb tokens have real defaults. --cui-breadcrumb-bg, --cui-breadcrumb-border-radius and --cui-breadcrumb-font-size were null in Sass, so the first two were emitted empty (--cui-breadcrumb-bg: ;) and the third was not emitted at all. They are transparent, var(--cui-radius-5) and inherit now. Nothing renders differently on a default breadcrumb, and a font size set on an ancestor still reaches it — the one visible change is that a breadcrumb given a background now has rounded corners like every other surface. Set --cui-breadcrumb-border-radius: 0 to square it off.
  • --cui-breadcrumb-divider is now declared on .breadcrumb, so set it there and not on a wrapper. The property was read but never emitted, which left it out of DevTools and out of the CSS variables table, and meant a value set anywhere above the list reached the separators by inheritance. It is a real token now — and a token declared on .breadcrumb beats one inherited from an ancestor, so <nav style="--cui-breadcrumb-divider: '>'"> stops working. Move it onto the <ol class="breadcrumb">.
  • A custom divider now survives in RTL. --cui-breadcrumb-divider-flipped defaults to the main divider instead of to a second copy of the Sass default, so setting only --cui-breadcrumb-divider no longer leaves right-to-left pages on the built-in /. Set the flipped one only for a separator that points somewhere — > becomes < — as before.
  • New: .breadcrumb-link, an opt-in class that gives a step a padded, hoverable target. Bare links keep rendering as they always did. On a <button> it looks identical to a link, which is what lets one step toggle a menu of collapsed items — the composition is documented under Collapsed items, together with the reason not to reach for role="menu" there.
  • New: .breadcrumb-divider, a separator you can put in the markup. The automatic ::before divider stays exactly as it was and existing markup is untouched, but a <li class="breadcrumb-divider"> placed between two items carries whatever you put in it — an inline SVG, an icon, a character — with no URL escaping and no variable to set, and an empty one renders the default divider. The automatic divider steps aside wherever an element is placed (.breadcrumb-item + .breadcrumb-item stops matching), so the two never double up, and the spacing is identical either way. Give the element aria-hidden="true", since a screen reader would otherwise count the separators as steps in the trail.

Avatar

  • The avatar carries its own colours, and .theme-{color} tints it. --cui-avatar-bg and --cui-avatar-color are new: a bare avatar is a neutral circle instead of a transparent one, and a .theme-* class puts the theme colour behind the letters and the colour that reads on it in front of them. The docs used to reach for bg-{color} plus a hand-picked text-*, which fails WCAG AA on five of the six examples they shipped — measured 1.85 on bg-warning text-white, 2.94 on info, 3.50 on success, 3.69 on danger, and 3.12 on bg-secondary, which carried no text colour at all. Every theme colour now lands between 4.56 and 18.03. Background utilities keep working on an avatar; they just no longer have to.

  • New: .avatar-subtle, a tinted avatar that keeps the theme colour in the letters rather than behind them.

  • Breaking One size token replaces the width/height pair. --cui-avatar-width and --cui-avatar-height always carried the same value, in the base and in all four size classes, so setting a size meant writing it twice. They become --cui-avatar-size, and --cui-avatar-status-width / -height become --cui-avatar-status-size the same way.

    The label is derived from it — calc(var(--cui-avatar-size) * .4) — rather than listed per size. That ratio is what every size already used, so nothing renders differently; --cui-avatar-font-size still overrides it where a size needs its own.

    The Sass variables follow: $avatar-width / $avatar-height / $avatar-font-size / $avatar-status-width / $avatar-status-height become $avatar-size / $avatar-status-size plus $avatar-font-size-ratio, and $avatar-sizes keys drop to size and an optional status-size. The $avatar-widths map, deprecated since 5.1.0, is gone.

  • Breaking .avatar-img fills the avatar and crops instead of stretching. It was height: auto, which deformed every image that was not square; it is now height: 100% with object-fit: cover. Square images look the same.

  • Breaking The status indicator’s ring follows the theme. It was 1px solid $white, a hardcoded white that read as a mistake in dark mode. It now comes from --cui-avatar-status-border-color, defaulting to the body background.

  • Breaking A stacked avatar lifts on hover instead of pushing its neighbours. The hover changed margin-inline-end, which moved every avatar after it; it now uses transform, so nothing else shifts. $avatar-transition changes from margin .15s to transform .15s ease-in-out accordingly.

  • Stacked avatars wear a ring and stop pulling what follows them. Each avatar in a stack gets a border in the page background colour (--cui-avatar-stack-ring-width / -color), so overlapping photos stay separated; the last avatar drops its negative margin, which used to drag the content after the stack underneath it. The overlap is a token now — --cui-avatar-stack-spacing, the fraction of the avatar size — and .avatar-stack-xs through -xl size every avatar in a stack at once.

  • The status indicator follows .theme-{color} and is never invisible. .avatar-status reads the theme slot and falls back to the new --cui-avatar-status-bg (a neutral grey), so a bare indicator reads as “offline” instead of rendering as an empty ring. Background utilities keep working on it.

Alert

  • Breaking An alert without a theme class carries its own surface. --cui-alert-bg falls back to var(--cui-bg-1) instead of transparent, so a plain .alert no longer takes the color of whatever it sits on. Set --cui-alert-bg: transparent on the alert to restore the old rendering.

  • Breaking The alert lays its children out in a row. It is display: flex with align-items: start and --cui-alert-gap between children, so an icon next to a label needs no d-flex and no spacing utility. Text mixed with inline elements is a single anonymous item and is unaffected, but an alert built from several block elements — a heading, paragraphs, an <hr> — now sits side by side. Wrap that content in a .vstack:

    <div class="alert alert-success" role="alert">
  <div class="vstack">
    <h4 class="alert-heading">Great job!</h4>
    <p>…</p>
  </div>
</div>

  • Breaking A solid alert is .alert-solid, not a pile of utilities. The docs used to say to drop the contextual class and reach for bg-{color} plus a text-* class picked by hand — and the examples hard-coded text-white, which fails WCAG AA on five of the eight theme colours: measured 3.50 on success, 3.69 on danger, 2.94 on info, 1.85 on warning and 1.10 on light, where white text on a near-white background is invisible. .alert-solid reads the theme’s own contrast token, so every colour lands between 4.56 and 18.03 — including a theme colour you define yourself. Markup using the old recipe still renders; it is the contrast that was never right.

  • An alert marked .fade show fades in when it is added to the page. The classes used to animate the alert in one direction only, because an element inserted with .show already on it has no earlier state to transition from; @starting-style supplies one. Nothing to change in your code — an alert you append at runtime animates without the class juggling that used to be needed, and an alert already in the markup is unaffected.

  • The close button is a flex item, not an absolutely positioned one. It is pushed to the end with margin-inline-start: auto, so it no longer overlaps the text and the alert no longer reserves three paddings of room for it. A .btn-close that is a direct child of the alert still lands where it did, with or without .alert-dismissible, and .alert-dismissible itself is now an empty class kept for existing markup. One case does change: a close button nested inside a wrapper used to be positioned by the alert, and is now laid out by that wrapper like any other content. Move it up to be a direct child of the alert to keep it at the trailing edge.

  • An <hr> inside an alert takes the alert’s border colour. The alert redeclares --cui-hr-border-color from the theme’s border colour, falling back to --cui-alert-border-color, so a separator in a .theme-success alert is green rather than the page’s neutral grey, and one in an alert whose border you recoloured follows it. A variant such as .alert-solid paints its border with the surface colour, so there the separator takes the theme’s border colour, or the text colour without one.

  • Breaking --cui-alert-border is gone. The border is written in the rule from --cui-alert-border-width and the border colour, so that a .theme-* class can colour it. Set --cui-alert-border-width and --cui-alert-border-color instead, and border-style on the alert for a dashed or dotted line.

  • Breaking $alert-dismissible-padding-r is gone; the space for the close button follows --cui-alert-padding-x. The variable was multiplied out in Sass when the stylesheet was built, so raising --cui-alert-padding-x widened three sides of a dismissible alert and left the fourth on the default: at 2rem the alert had 32px of padding and 48px of room for the button, which also kept its own 16px padding. Both are subtracted from the tokens now — calc(var(--cui-alert-padding-x) * 3) and calc(var(--cui-alert-padding-y) * 1.25) var(--cui-alert-padding-x) — so one token resizes the whole alert. Defaults render as before; drop any override of the removed variable.

The close button is masked, not filtered

Breaking

.btn-close used to paint a black glyph baked into its SVG and recolour it for dark mode with a filter. The colour now comes from the element, the way the check, radio, carousel and toggler icons already work:

- background: transparent var(--cui-btn-close-bg) center / 1em auto no-repeat;
- filter: var(--cui-btn-close-filter);
+ background-color: currentcolor;
+ mask-image: var(--cui-btn-close-icon);

  • $btn-close-color defaults to inherit, so the glyph follows the surface it sits on. A close button inside a themed alert or a dark toast no longer needs a rule of its own to stay legible.
  • Breaking .btn-close-white is gone, deprecated since v5.0.0, and so is the dark-mode rule that forced the glyph white. Both restated what the inherited colour already produces on a surface that paints its own text — a .text-bg-inverse toast, a dark navbar’s offcanvas, a .bg-body.text-body section under data-coreui-theme="dark". Delete the class; the button renders identically without it. The rule additionally got the mirror case wrong: a data-coreui-theme="light" section inside a dark page inherited the forced white and drew a white icon on white.
  • Breaking --cui-btn-close-width and -height become --cui-btn-close-icon-size. The glyph is square, so one variable sizes it; the padding keeps both axes (--cui-btn-close-padding-y, -padding-x). Nothing changes on screen: the glyph is still 1em inside .25em of padding, so the pointer target stays 24px at the default font size — the WCAG 2.2 minimum.
  • Breaking --cui-btn-close-bg is --cui-btn-close-icon ($btn-close-bg → $btn-close-icon). It stopped being a background when the glyph moved to a mask; the name had been describing the old implementation.
  • The SVG in --cui-btn-close-icon carries the shape only. A custom image works the same way — give it any colour, the mask ignores it.

Badge

  • Breaking Colour comes from .theme-*, and .badge-* now names the variant. A bare .badge used to be white text with no background of its own, so it was invisible until a .text-bg-* utility supplied both. It renders neutral on its own now — --cui-badge-color is inherit and --cui-badge-bg is --cui-bg-2 — and a .theme-* class colours it: <span class="badge theme-danger">. The .badge-* namespace carries the three variants instead: solid (default), .badge-subtle and .badge-outline, each mapping the same theme roles.

    .text-bg-* still works and still sets both properties, so existing markup keeps rendering. Markup that paired .badge with a background utility alone (<span class="badge bg-danger">) now shows the inherited text colour on that background instead of white — swap it for .theme-danger or add a text colour utility.

  • The badge lays itself out. display is inline-flex with --cui-badge-gap between children and --cui-badge-min-height as the floor, so an icon next to a label needs no spacing utility and badges keep one height across a table or a list.

  • The font size has a legibility floor. --cui-badge-font-size is clamp(12px, .75em, .75em), so a badge inside small text stops shrinking at 12px while still scaling up with a larger parent.

  • New: .badge-position-{top|bottom}-{start|end}. One class pins a badge to a corner of its positioned parent, centred on the corner, and flips with the writing direction. It replaces the position-absolute top-0 start-100 translate-middle utility stack the docs used to recommend; that stack still works. The .btn .badge nudge (position: relative; top: -1px) is written as .btn :where(.badge) so a position class on a badge inside a button wins; a stylesheet that relied on beating .btn .badge with two classes now beats it with one.

  • New: --cui-badge-border-width / --cui-badge-border-color (transparent), .badge-lg, and a link reset. The border tokens are what .badge-outline switches, .badge-lg joins .badge-sm on the size scale, and a.badge no longer inherits the underline from the reboot.

Carousel slides by scrolling

  • Breaking The engine is native CSS scroll snapping, not transforms. The track (.carousel-inner) is a scroll container: dragging, swiping and momentum come from the browser, and programmatic jumps animate the scroll position over a fixed 300ms. The transform choreography is gone with its state classes — .carousel-item-next, .carousel-item-prev, .carousel-item-start, .carousel-item-end and .pointer-event no longer exist; react to the slide/slid events instead of styling them. The .slide class is inert — leave it in old markup or drop it, nothing reads it any more. The markup skeleton (indicators + inner with items + controls) is unchanged, and the controls, indicators and captions keep their overlaid layout.
  • Breaking ride is autoplay, wrap is ends, and touch is gone. data-coreui-autoplay="true" (boolean — the "carousel" spelling is gone) cycles from page load; ends takes "loop" (default — continues seamlessly where the layout allows), "wrap" (the old jump) or "stop" (hard ends with the matching control disabled). Touch needs no option: the browser owns it. Autoplay now turns off for good once the user interacts (WCAG 2.2.2), and while it runs the active indicator fills like a progress bar over the slide’s interval.
  • New layout knobs and a pause control. --cui-carousel-items, --cui-carousel-items-gap and --cui-carousel-items-peek put several slides in the viewport; .carousel-center snaps the active slide to the middle and .carousel-auto lets slides keep their own width. A button with .carousel-control-play-pause (holding .carousel-control-pause-icon and .carousel-control-play-icon) toggles autoplay and swaps its aria-label between data-coreui-pause-label and data-coreui-play-label.
  • Breaking .carousel-dark, the carousel-dark() mixin and $carousel-dark-* are gone. The chrome colours are light-dark() pairs resolved on the carousel itself, so the standard data-coreui-theme="dark" attribute is the dark variant — and data-coreui-theme="light" pins the white chrome on a dark page the same way.
  • Every chrome measurement is a --cui-carousel-* token declared on .carousel — control width and opacities, icon images and sizes, indicator geometry and transitions, caption metrics, the play/pause button — so the whole carousel restyles at runtime without recompiling.
  • Crossfade timing moved to tokens. $carousel-transition-duration and $carousel-transition are gone; the fade reads --cui-carousel-fade-duration and --cui-carousel-fade-timing, and the slides stack on a grid instead of floating.

  • Breaking Multi Select opens a dialog instead. The panel is role="dialog" named by the control, and the focus moves into it: onto the search box when search is on, otherwise onto the option the list points at. Typing reaches the search box from anywhere in the component by default, which is what 'global' used to turn on, so data-coreui-search="global" becomes data-coreui-search="true". Set globalSearch: false to keep typing local: the search box then filters only while it has the focus, and a keystroke over the options list jumps to the first option starting with it. Any other string throws a TypeError.

  • Breaking Multi Select’s value wins over options marked selected. It used to add to them, in the markup and in options, and later options applied the start value again; now a given value is the selection, also for options that arrive later for the first time, as in the React and Vue editions, while options shown before keep their state. An array of numbers matches the options, and value: '' reads like an empty data-coreui-value.

  • Multi Select takes search: 'external'. The search box then filters nothing, search.coreui.multi-select carries the query, and setOptions() replaces the options without rebuilding the control or touching the selection; a selected value the new options lack keeps its chip and is still sent with the form, unless it is disabled. setLoading() shows a loadingLabel row below the options meanwhile, and they stay usable. resetSelectionOnOptionsChange empties the selection when the new options carry different values, for options that depend on another field.

  • Multi Select’s search.coreui.multi-select follows the text, not the keys. It fires when the text of the search box changes, a paste included, and no longer on a key that leaves the text alone, such as an arrow, or when the panel opens or closes over an empty box.

  • Multi Select’s dispose() gives the native select back the options it had before the component started. A select built from options in the config, or one whose options setOptions() replaced, used to keep the generated options; an empty <select> given options is empty again after dispose().

  • Breaking Multi Select sends one change.coreui.multi-select per change of the selection. The clear button, deselectAll(), selectAll() and a pick that replaces the value of a single select used to send one event for every option they touched; they send one now, once the native select holds the new value and the control shows it, the way the native change works. An action that changes nothing sends no event, native ones included, and the component no longer sends one for each preselected option while it builds or rebuilds. A selection the page gives sends none, from setValue() or from a given value that options from setOptions() bring later, and a native reset of the form that changes the selection sends one, as Autocomplete, Chip Input and Combobox do.

  • Breaking Form controls fire their change event once per change of the value, on a form reset as well, and never from a value the page gives. OTP Input’s change.coreui.otp-input, Rating’s reset(), Autocomplete’s clear() and Range’s changed.coreui.range used to fire even when the value stayed; they fire only when it changes now, and Range no longer fires while it starts or on the change after an input. OTP Input and Range Slider now fire on a native form reset that changes the value, and Date Input sends the native input and change of its value field there too. setValue() of OTP Input does not fire. A form reset brings Rating and Range Slider back to the value they were created with, not one a later setValue() gave, and OTP Input’s reset() puts back the code it started with, as a native reset does. A stepper keeps the validation marks of a form reset a listener cancels.

  • Multi Select keeps its selection through setOptions(); it used to fall back to the options marked selected. A selected option that is disabled, also inside a disabled group, shows as a disabled chip and stays through the clear button, deselectAll() and Backspace; the options of a disabled group are disabled in the list and in the native select as well, so, like any disabled option, they are not sent with the form. A single select whose selection is empty holds its value="" placeholder option, or none, instead of letting the browser fall back to the first option, so the form gets no option the control does not show.

  • Breaking Autocomplete’s search takes only 'external', and global typing is globalSearch, on by default. The array and the comma list are gone, so search: ['external', 'global'] and data-coreui-search="external, global" become search: 'external', and search: 'global' goes away: typing on the picker or clear button, or in the panel, reaches the field without it. Set globalSearch: false to keep a keystroke where the focus is. An array now fails the option type check, so new coreui.Autocomplete(el, { search: ['external'] }) throws until it is updated, and a string other than 'external' no longer turns external search on, so a page still writing the comma list in a data attribute filters the server’s results again. The space bar and shortcuts with Ctrl or Cmd stay with the button that has the focus.

  • Autocomplete no longer gives the host tabindex="-1" and keeps a tabindex the page wrote out of the tab order while it lives, so the field is the only tab stop; a click on the frame puts the focus in the field rather than only opening the panel. With search: 'external' the panel opens for the options you set even when they do not contain the typed text.

  • Breaking Autocomplete’s typeahead hint no longer reaches the server. With showHints on, the hint input behind the field carried a name and, being readonly rather than disabled, was serialized with the form: the configured name when there was one, <uid>-hint when there was not. A form therefore submitted either the field twice with an empty string in front of the value, or an extra …-hint key nobody asked for. The hint now carries no name, so new FormData(form).getAll(name) returns one entry and form.elements[name] is an input rather than a RadioNodeList. Code written around the old shape, such as reading getAll(name)[1], needs the plain value.

  • Breaking Multi Select’s search field no longer reaches the server. The input that filters the options carried a name and is a plain text input, so every form holding a Multi Select submitted whatever the user had typed to narrow the list: search-<name> when the select had a name, search-<uid> when it did not. It carries no name now, the search-… key is gone from the payload, and the input sets autocomplete="off" so the browser stops offering to fill it.

  • Breaking An unnamed Multi Select stays out of the form. A <select> the page had not named was given name="<uid>", so its value was submitted under a key nobody chose. The attribute is written only when there is a name, from the option or from the element. dispose() also takes back the id and the name the component added, where it used to leave both behind.

  • Breaking An unnamed Autocomplete stays out of the form too. Its input took a generated name when the option was not set, so a form carried a key nobody chose. It does not now. The generated id is unaffected.

  • Breaking Validation state comes from validationState. invalid and valid are deprecated aliases of validationState: 'invalid' and 'valid', and validationState also takes a state from $form-validation-states. A given 'invalid', from the options or from an .is-invalid class in the markup, now blocks the submit, and the next change the user makes to the value drops it, while a change from code keeps it. The markup class is read once, when the component starts, so it no longer comes back when the text returns to the value it started with, a native form reset drops it, and a class written later is not read. A validation that reports the input, from a submit or the page’s own checkValidity(), now shows on the frame, and the autocomplete is the only one that writes aria-invalid and the message link on its input: the form plugin and the stepper leave the input to it. See Validation.

Calendar

  • Changed. The range band sits under the day cells and follows the theme. --cui-calendar-cell-range-bg is --cui-primary-bg-subtle (the theme’s bg-subtle under a .theme-* class) instead of a 12.5% tint laid over the cells, so the selected start and end keep their solid fill and the day numbers are no longer tinted. A hovered day in the range takes --cui-primary-bg-muted (the theme’s bg-muted), one step stronger than the band.
  • Changed. minDate and maxDate are compared by the day. v5 compared a day cell at midnight with the instant, so a limit that carried a time of day, such as minDate: new Date(), disabled its own day. Now that day can be picked; the Date Picker’s time selects and the field bound the time on it.
  • Changed. A week row stands for the ISO week that holds most of its days. With firstDayOfWeek other than 1 a row spans two ISO weeks, and v5 numbered it by its last day but picked the week of its first day: a Sunday-first row from August 30 to September 5, 2026 showed 36 and picked 2026W35, and that value given back as startDate did not select the same row. The number, the picked value, the weeks of startDate, endDate, minDate and maxDate, and the range and its preview now all follow the row’s majority week, so that row is 2026W36 and the picked date is its Monday, August 31, the date 2026W36 stands for. With Tuesday to Thursday first, the numbers move instead, so the row from September 1 to 7 shows 36 where it showed 37.
  • Changed. In week selection disabledDates disables a week only when it disables every day of it, as it does for a month, quarter or year. Before, a week was disabled when its row’s first day was: with Monday first disabledDates: [new Date(2026, 7, 31)] disabled week 36, and with Sunday first a function that disables weekends disabled every row. A range of weeks across a week that holds a disabled day is kept, as a range of months is.
  • Changed. In week selection minDate and maxDate count as whole weeks, so their weeks can be picked on any first day of the week, as the month, quarter or year of a limit can in those selections, and the months view opens a month only when its page holds a week inside them. Before, a minDate later than the first day of its row disabled that row, and with Tuesday to Thursday first a maxDate of 2026W36 disabled the row of week 36.

To follow the pointer or the focus over a calendar, listen for mouseover or focusin on its element: each day, month, quarter and year cell the calendar shows carries its date in data-coreui-date, in the toDateString() form, and a week row carries it on the day cells it shows. Unlike the event, the listeners also see cells that cannot be picked, and only mouseout or focusout tells that the pointer or the focus left.
  • Breaking selectAdjacementDays and showAdjacementDays are spelled selectAdjacentDays and showAdjacentDays — the option keys, the data-coreui-select-adjacent-days / data-coreui-show-adjacent-days attributes and the picker passthrough alike. The typo is fixed in the React and Vue libraries in the same release.
  • Breaking update(config) is gone; the dates change through setStartDate(), setEndDate() and setCalendarDate(), and the other options are fixed once the calendar starts. A call like update({ startDate }) used to reset every other option (range, calendars, locale, …). See Live changes go through setters, not update(config).
  • Breaking Each grid is one tab stop, and tabindex no longer marks a selectable cell. The arrows, Home, End and the page keys move within a calendar and Tab leaves it, which is what role="grid" promises. Every cell inside minDate / maxDate can take the focus, also one that cannot be picked: the keys stop on a date in disabledDates instead of skipping it, a screen reader announces it as unavailable, and Enter and Space do nothing there, so a month where nothing can be picked is explored like any other.   • Breaking Day cells write data-coreui-date in the toDateString() form ("Thu Sep 17 2026"), like the month, quarter and year cells, instead of the full Date#toString() value. A script that selected a day cell with [data-coreui-date="${date}"] needs [data-coreui-date="${date.toDateString()}"].

A picked day of an adjacent month (selectAdjacentDays) used to become the calendar date while the grid stayed put, so the next-month button then skipped a month; it now stays where it was and shows as selected with an outline on a subtle background instead of the solid fill (--cui-calendar-cell-selected-adjacent-color, --cui-calendar-cell-selected-adjacent-bg, --cui-calendar-cell-selected-adjacent-hover-color, --cui-calendar-cell-selected-adjacent-hover-bg).   • In the years view the navigation names the page it shows, 2020 – 2031, instead of the one year the page is built around, so turning a page is announced as the new range. The grid label and the navigation write the range in the locale’s own digits.
  • In the years view the double arrows and Page Down / Page Up turn the calendar by the twelve years a page shows instead of ten, so a turn no longer repeats two years of the previous page.
  • In the years view the year button goes back to the view that picks the date instead of doing nothing, and it is disabled in year selection, where the years view is the one that picks.
  • Without weekNumbersLabel the week-number column is named for screen readers with the locale’s word for week, in a visually hidden span; before, its header was empty. Each week number is named the same way with its number (Week 36), and the new ariaWeekNumberLabel option takes a function of the week number to name it yourself.

Date Picker / Date Range Picker

Breaking

The pickers are rewritten. DatePicker, DateRangePicker and TimePicker are now a composition of the section-based input fields (date input), the calendar and a shared popup primitive, instead of the v1 monolith. The rewrite ships under the existing names — DatePicker, data-coreui-date-picker, .date-picker — so no renaming is needed on your side, but the options below changed. The v1 shells are gone; if you need to compare against the old behaviour, v5 is the reference. Mapping:

  • Removed — projected regions replace button configuration. footer, todayButton, todayButtonClasses, cancelButton, cancelButtonClasses, confirmButton, confirmButtonClasses, ranges, rangesButtonsClasses → put a <template data-coreui-template="footer"> / data-coreui-template="ranges" child in the picker element. Zero-argument actions bind with data-coreui-picker-action="today|clear|reset|close"; actions with arguments (range presets) go through picker.getContext() (setDate, setRange, clear, reset, close + read-only state).
  • Removed — obsolete with section fields. inputDateFormat, inputOnChangeDelay, inputReadOnly, placeholder — the masked field is always a valid partial date; there is no free-text parsing to debounce. Section placeholders come from the section fields’ own per-section options — dayPlaceholder, monthPlaceholder, yearPlaceholder and the rest.
  • Removed — previewDateOnHover and separator on the date range picker. The fields no longer preview the hovered day in a second, read-only input; the calendar still highlights the range up to the hovered day. The separator between the two fields is always rendered, and separatorIcon / separatorIconRtl replace its icon.
  • Kept. timepicker: true still adds the time half to the date picker, now as a row of time selects under the calendar rather than a second panel beside it. Because the two halves own different parts of one value, a picker with time does not auto-close: picking a day keeps the time and picking a time keeps the day. seconds narrows what the time half offers and selectionOptions is its escape hatch.
  • Changed. With timepicker, a minDate or maxDate that carries a time of day bounds the time on its day: the time selects disable the hours, minutes and seconds before minDate or after maxDate there, a time the panel sets beyond the limit (the current time when that day is picked) moves to the limit, and a typed time beyond it marks the field invalid. A limit without a time of day covers its whole day.
  • Kept. Calendar passthrough (locale, minDate/maxDate, disabledDates, selectionType, showWeekNumber, custom cell renderers, …), container, startDate/endDate/date, startName/endName/name, size, validation states, the data API (data-coreui-date-picker), and the imperative API (show/hide/toggle/clear/reset).
  • Passthrough is by name. Options that belong to the inner calendar or date input are forwarded automatically, so data-coreui-selection-type, data-coreui-show-week-number and data-coreui-format work on the picker element. calendarOptions / inputOptions remain as the programmatic escape hatch.
  • Every selection type has a matching mask. Month and year selection narrow the mask to MM/yyyy and yyyy. Week selection renders the native <input type="week"> presentation — a fixed localized label plus week and year sections (Week 29, 2026, Tydzień 29, 2026), where the year is the ISO week-numbering year. Quarter selection narrows to QQQ yyyy (Q4 2026). The v1 text input rendered 2026W27/2026Q1; the submitted value now follows the mask (set format="yyyy-Www" for an ISO-style field), and the event carries the v1-formatted string in event.formattedDate next to the Date in event.date (see “Picker events can be cancelled” below). The format parser gained ww (ISO week) and q/QQQ (quarter) tokens, plus quoted literals ('Week' ww — fixed text that may contain token letters, '' escapes a quote).
  • Format comes from the mask. inputDateFormat is replaced by format (forwarded to the field); inputDateParse still applies to pasted text.
  • Footer buttons are projected, today/now actions keep the v1 gating. A projected button opting into the today action (now on the time picker) is disabled at initialization when its target falls outside minDate/maxDate/disabledDates — matching the v1 built-in button. This is one-way: the picker only ever sets disabled, never re-enables. The state of any other projected button is yours — the slot context exposes isDateSelectable(date) (isTimeSelectable on the time picker) for computing it.   • The calendar is built on first open, not at construction. It accounts for ~83% of a date picker’s DOM (and ~89% of a range picker’s), and it is not observable before the popup opens, so the shells create it in show() and seed it from the field values. Measured over 20 pickers: date picker 65 ms → 15 ms and 3200 → 540 DOM nodes, range picker 93 ms → 12 ms and 6060 → 740 nodes. The first open costs a few milliseconds more (the calendar is built then); later opens are unchanged. Code reaching into the private picker._calendar before the first open now finds null.
  • setRange() and reset() on the Date Range Picker show the range in the calendar, on the month of its start date (of its end date when there is no start), in whatever view the calendar is in and also when the range does not change, so a preset clicked again after browsing brings its range back. The calendar used to move only when a field changed, and went to the month of the end date when both changed. clear() leaves it where it is; setDate(), today() and reset() on the Date Picker already showed their date.

-   <input type="password" class="form-control">
-   <button type="button" class="form-control-action" data-coreui-toggle="password" aria-label="Toggle password visibility">
-     <span class="form-password-action-icon"></span>
-   </button>
- </div>
+ <input type="password" class="form-control" data-coreui-password-input>
  • data-coreui-toggle moves from the button to the input, and its value is the component’s name: password-input (and number-input for the new Number Input). The button no longer exists in your markup, so there is nothing left to put it on.
  • Classes you write on the input, other than .form-control, move onto the frame — size, spacing, width. They describe the field, and once the input is wrapped the field is the frame; a margin left on the control would sit inside the border. They move back on dispose().
  • An input already inside a .form-control-group is left where you put it, so a field can share a frame with other adornments, and only a frame the component created is removed on dispose().
  • The accessible name of the toggle is the ariaToggleLabel option now, since the button is no longer yours to label.

Breaking

Icons rendered by JavaScript

ScrollSpy

  • Breaking The active link is chosen by an activation line, not by scroll direction. The plugin used to compare each section’s offset with the previous scroll position, so the same scroll offset could highlight a different link depending on which way you arrived. It now activates the lowest section whose top edge has crossed a line drawn topMargin below the top of the scroll container — a pure function of the scroll position. Two visible consequences: the last active link stays highlighted while a gap between sections crosses the line (the navigation no longer goes blank), and a short last section is activated when the container is scrolled to the bottom, even though its top never reaches the line.
  • New option topMargin (default 12%) places the activation line; it takes a percentage of the container’s height or a pixel value (96px). A pixel line is recomputed on resize.
  • Breaking rootMargin defaults to null and is now the raw override. Set it and it is handed to the IntersectionObserver unchanged, taking precedence over topMargin; a v5 configuration such as rootMargin: '0px 0px -25%' keeps working as written. threshold defaults to [0] instead of [0.1, 0.5, 1] — with an activation line a section only needs to report whether it crosses it.
  • smoothScroll finishes the navigation. Once the scroll settles, the URL hash is replaced with the link’s target and focus moves to the section.
  • Breaking The deprecated offset option is removed — it has been a thin alias since the IntersectionObserver rewrite. Use topMargin instead: offset: 100 → topMargin: '100px'.

  • The data-coreui-toggle="pill" and "list" toggles stay — they are documented markup, and v6 keeps documented markup working.
  • $nav-link-transition splits into $nav-link-transition-property/-duration/-timing, emitted as --cui-nav-link-transition-*. The link’s transition was compiled into its rule while .tab-pane in the same file already read the three-token form, so half the file could be retimed in the browser and half could not. Setting --cui-nav-link-transition-duration now takes effect; before it was ignored.

The link lays its children out with --cui-nav-link-gap, --cui-nav-link-align and --cui-nav-link-justify, so an icon and its label line up without a wrapper. It also takes --cui-nav-link-hover-bg and --cui-nav-link-active-bg, rounded by --cui-nav-link-border-radius — the base nav used to change text color alone. Tooltip

  • --cui-tooltip-opacity now blends into the background colour instead of fading the whole element. The old element-level opacity: .9 also faded the label text, compositing it below the WCAG 1.4.3 contrast minimum (about 3.5∶1). The surface and arrow keep the same translucent look; the text renders at full opacity. The token still works — override it and only the background alpha changes.
  • Breaking $tooltip-margin and --cui-tooltip-margin are removed. The variable had been null and deprecated since v4; the token compiled to an empty value and the margin declaration reading it never took effect. Position a tooltip with the JS offset option instead.
  • Roomier tip, less see-through. --cui-tooltip-padding-y is calc(var(--cui-spacer) * .375) (was .25rem), --cui-tooltip-padding-x is calc(var(--cui-spacer) * .75) (was .5rem) and --cui-tooltip-opacity is .95 (was .9). Set the three tokens on .tooltip to keep the old proportions.

OTP input

  • The plugin is enabled with a bare data-coreui-otp. data-coreui-toggle="otp" no longer initialises anything. The toggle attribute marks a control the user activates — a button, a link, an input that opens a panel — and the OTP field is none of those: it is a wrapper the plugin builds its slots inside. Chip Input, Multi Select and the masked date and time fields already read that way.
  • A code delivered by SMS autofill or a password manager now fills the whole field. Only the first slot carries autocomplete="one-time-code" (the rest are off), and a multi-character value arriving in any slot is spread across the field, as a paste already was. Previously such a value stayed in one slot and the submitted value was empty. The slots also gained enterkeyhint, autocorrect="off" and spellcheck="false".
  • Breaking Only the hidden input carries the field’s name. Each visible slot was given <name>-<index> on top of it, so a six-slot field submitted seven keys where the option is documented as the name of the hidden input. The slots are unnamed now, and a name or an id written on a slot in the markup is left alone instead of being overwritten. The hidden input carries whatever the slots show, so slots rendered with their own value attributes are submitted as well, which they were not before.
  • In a right-to-left field, linear now holds the forward move rather than the ArrowRight key. Forward is ArrowLeft when the field reads right-to-left, so that is the key a linear field stops on an empty slot, and ArrowRight walks back freely. Previously the guard was attached to the key name, which let the caret jump ahead over empty slots in RTL and refused to walk back.
  • Breaking The code is validated as one value. It moved from an <input type="hidden">, which the browser leaves out of validation, to a text input laid invisibly over the group, with tabindex="-1" and aria-hidden="true", a pattern for the full length of the code and the required that the slots used to carry. A required code that is empty or incomplete stops the submit, so does an incomplete code that is not required, and the browser puts focus on the first empty slot with its own message over the group. Once a validation reports the code, the group gets .is-invalid and every slot carries aria-invalid="true" and is described by the message after the group while the code stays invalid. The stylesheet colours every slot and shows that message, which it never did for a slot marked invalid. Code that selects input[type="hidden"] inside the field needs .form-otp > input:not(.form-otp-control), a slot no longer gets required, and a data-coreui-invalid-feedback written on the slots goes on the .form-otp element.
  • The code takes a validation state. The new validationState option, or an .is-invalid/.is-valid class on the .form-otp element or on a slot in the markup, shows the state on the group and the slots, and 'invalid' blocks the submit. A class on one slot, which used to colour only that slot, now marks the whole code. The user’s next change of the code drops it, setValidationState() sets it again, and a native form reset puts back the code the field started with. A change of the code sends input and change from the input that holds the value.
  • Breaking The readonly option is removed, and every slot is editable. A code the user cannot type has no use in a form, so data-coreui-readonly, { readonly: true } and a readonly written on a slot no longer make it read-only; use disabled to show a code the user cannot change.

Rating

Both spellings now agree with the HTML attribute: data-coreui-read-only="true" becomes data-coreui-readonly="true", and new Rating(element, { readOnly: true }) becomes { readonly: true }. A read-only rating without name still submits nothing.
  • A star with keyboard focus shows the focus ring.
  • The setters keep the value the user picked and the stars. setValue(), disable() and enable() change their part in place; any option change through update() used to render the stars again and reset the rating to its initial value.
  • Breaking The rating takes a validation state. The new validationState option, or .is-invalid/.is-valid on the rating element read once when it starts, colours the focus ring, and a given 'invalid' sets aria-invalid on the group and blocks the submit until the user picks or clears a star or the form is reset. A class written on the element later is not read; set the state with setValidationState(). See Validation.

  • Empty stars are --cui-fg-4: gray-500 in the light scheme and gray-600 in the dark one, the lightest grays that keep 3:1 against the page background. The empty stars of v5 were 38% of the text colour, below 3:1 against the page in the light scheme.

Search Button

  • Breaking The shortcut handlers no longer create search button instances. Every keydown, keyup and window blur anywhere on the page used to initialise each [data-coreui-search-button], so dispose() lasted until the next key press. Now the buttons in the document at DOMContentLoaded are initialised, and a button added later, or one on a page whose script runs after DOMContentLoaded, responds to its shortcut once you call coreui.SearchButton.getOrCreateInstance(element). Activating such a button (a click, or Enter or Space on it) still initialises it.

Alert

  • Breaking Every alert fades out when dismissed, and .fade no longer decides that. The alert carries its own transition and --cui-alert-transition-property / -duration / -timing; the JavaScript marks it with .hiding for the length of it, then removes the element. An alert is already on the page, so only the exit is animated — .fade and .show remain the way to fade one in when you insert it at runtime. Add .alert-instant to an alert that should go at once, which is what an alert without .fade used to do. Add .transition-size next to .fade and the exit takes the box with it, so the page rises into the alert’s place instead of jumping.

The class keeps working — and is still the way to go when the button is injected later or sits inside a wrapper — so no existing markup changes.

Chip / Chip set / Chip input

  • Breaking A chip starts selected only from the selected option. An active class in the markup no longer selects it; write data-coreui-selected="true" on the chip instead. The role, tabindex and aria-* a chip or a chip set writes come from its options too, so a role or tabindex in the markup is replaced rather than kept, and dispose() leaves them in place for the next instance to rewrite.
  • A chip set is one tab stop. The set keeps tabindex="0" on one chip and -1 on the others and moves it with the focus, so Tab enters and leaves the set once and the arrow keys move between the chips. Every interactive chip used to be a tab stop of its own.
  • Chips expose real roles now. A selectable chip set is a horizontal role="listbox" (with aria-multiselectable in multiple mode) whose chips are role="option" elements carrying aria-selected; a standalone selectable chip is a toggle button (role="button") reflecting its state via aria-pressed instead of aria-selected; a non-selectable set is a role="group". aria-disabled is only stamped on chips that carry a role — on a role-less chip the attribute was invalid and is now removed.
  • clear() and removeSelected() report the change once. Chip set and Chip input fired change and select (.coreui.chip-set/.coreui.chip-input), and Chip input its native input and change, once for every chip removed; they fire once now, after the last chip is gone, and not at all when the chips did not change. The cancelable remove still fires for every chip.
  • Adding and removing chips is announced. Chip set and Chip input announce each change through announce(); the wording is configurable via ariaAddedAnnouncement/ariaRemovedAnnouncement.
  • Every remove button names its chip. Chip and Chip set named each remove button Remove, so a set read the same name for every chip; the button is Remove <text> now, as Multi Select already did; Chip input names it after the chip’s text instead of its value. ariaRemoveLabel (and Multi Select’s ariaChipRemoveLabel) takes a string, where {label} stands for the chip’s text and is appended when missing, or a function of the text for a different word order. A one-word label such as Usuń gains the text; a label that already spelled the text out, such as data-coreui-aria-remove-label="Remove React", now repeats it, so drop it or use {label}. A .chip-remove button you write yourself keeps its aria-label, and gets one from ariaRemoveLabel when it has none.
  • A selectable chip hides its remove affordance. A chip with a role — a selectable chip, which is a toggle button, or an option in a selectable set — gets a <span aria-hidden="true"> instead of a <button> inside it, so its name is its text and a control is no longer nested in a button. Backspace / Delete remove it from the keyboard, the affordance from the pointer.
  • Chip input: aria-disabled/aria-readonly are no longer stamped on the container. The container is a generic element, so those attributes were invalid on it (axe aria-allowed-attr); the native disabled/readonly states on the inner <input> carry the semantics.
  • The remove button gets its size back, and .chip-sm/.chip-lg resize everything they claim to. .chip-remove sized itself from a token that was never declared, so both dimensions were invalid at computed-value time and fell to auto — the button measured 0x0 at every chip size. It reads --cui-chip-remove-size now (16px, 14px on .chip-sm, 20px on .chip-lg), so a chip with a remove button is wider than it was.
  • .chip-dismiss is .chip-remove. The rename landed with the component; a single selector kept the old name and styled nothing, so a disabled chip input never reached its remove buttons through CSS. The button’s disabled attribute was doing the work on its own.
  • --cui-chip-dismiss-size is gone; use --cui-chip-remove-size. The size classes wrote the first name and the glyph read the second, so the remove icon stayed at its base size in every chip size. Nothing read the old token, so an override of it never did anything.
  • .chip-sm and .chip-lg no longer swap the image and icon sizes. They passed the two to chip-size() in the wrong order, so a large chip rendered its icon at 24px and its image at 20px — the reverse of the base sizes, where the image is the larger of the two. Large is now 24px image / 20px icon and small 16px / 14px.
  • Breaking The selected chip’s text follows the palette. $chip-active-color was white at 87% opacity, computed at build time — repaint the selected background and the text stayed near-white. It defaults to var(--cui-primary-contrast) now (solid, slightly brighter than before), and a .theme-* class supplies its own contrast colour through the slot.
  • Hovering a themed, unselected chip no longer previews the selected look. The background steps from bg-subtle to bg-muted and the text colour stays put; only selection paints the solid theme colour. A chip without a theme class hovers exactly as before.

Collapse

  • Breaking The toggle option is gone. It made the constructor change the state the markup declares, which surprised people — so nearly every caller passed toggle: false. The constructor now always keeps the declared state; add .show to start open, and call show(), hide() or toggle() to change it.

    - const collapse = new coreui.Collapse('#myCollapse', { toggle: false })
+ const collapse = new coreui.Collapse('#myCollapse')

    Callers that relied on the constructor toggling need an explicit call: new coreui.Collapse(el).toggle(). data-coreui-toggle on a trigger is unrelated and unchanged.

  • Breaking Triggers no longer get the .collapsed class. Their state was written twice, as the class and as aria-expanded, and only the second is required. Nothing in the stylesheet had matched the class since the accordion stopped using it, so it survived as a hook for custom CSS — style the attribute instead, which is also what assistive technology reads:

    - .accordion-button.collapsed::after { transform: rotate(-90deg); }
+ [data-coreui-toggle="collapse"][aria-expanded="false"]::after { transform: rotate(-90deg); }

  • New hiddenUntilFound option. With data-coreui-hidden-until-found="true" a collapsed area is hidden with hidden="until-found" rather than taken out of the layout, so the browser’s find-in-page searches it and expands it on a match; the component then syncs .show and aria-expanded so the declared state follows what the reader sees. Off by default, and below Chrome 102 / Firefox 148 / Safari 26.2 it hides the content the way hidden always did.

  • Breaking The transition is set through CSS variables, and the Sass variables split in two. $transition-collapse and $transition-collapse-width were shorthands carrying the property, the duration and the easing at once, which meant retiming a collapse required restating the property. They are replaced by $transition-collapse-property, $transition-collapse-duration and $transition-collapse-timing, emitted as --cui-transition-collapse-property / -duration / -timing on .collapse and .collapsing, so all three can also be changed per instance at runtime. $transition-fade splits the same way into $transition-fade-duration / $transition-fade-timing.

  • Breaking CSS owns the collapse animation, and the class choreography follows. Where interpolate-size: allow-keywords is supported the stylesheet interpolates the size to the auto of the open state on its own; elsewhere JavaScript measures the two sizes and the stylesheet still times the move. Three observable changes come with that:

    • .collapse never leaves the element. It used to be swapped out for .collapsing while the transition ran; now .collapsing is added alongside it, so .collapse.collapsing matches during a run and a selector keying on the absence of .collapse no longer fires mid-animation.
    • .show toggles at the start of both directions. It used to land at the end of the opening transition. A rule styling .collapse.show applies for the whole expansion now, and its absence marks the whole closing run.
    • An open .collapse-horizontal is fit-content wide, not as wide as its container — the open size is the animation’s target, and a target of auto would spend most of the run growing an empty box past the content. This also removes the end-of-animation jump to full container width the measured animation used to make. Style the child, as the docs always showed, and nothing changes.

Button

  • A toggle button always exposes aria-pressed now. The attribute has no default value, so a [data-coreui-toggle="button"] that shipped without one was announced as a plain button until the first click. JavaScript adds the missing attribute on DOMContentLoaded, reading the .active class to pick the value; an attribute you wrote yourself is left alone. Write it in your markup anyway, so the state is correct before our JavaScript runs.

  • Breaking .btn is a flex container. It lays its content out in a row, centres it on both axes and separates the parts with --cui-btn-gap, so an icon next to a label no longer depends on a whitespace text node in your markup — and no longer gets a second space where you did leave one. --cui-btn-min-height keeps a button that holds only an icon as tall as one that holds text. Custom CSS that positioned button content with display, line-height or margins needs a second look; the caret of a .dropdown-toggle now takes its distance from the gap instead of its own margin.

  • Breaking A button label no longer wraps. --cui-btn-white-space is nowrap. In v5 $btn-white-space was null, so no declaration was emitted at all and a long label broke onto a second line, leaving the button taller than the ones beside it — while the variable’s own comment told you to set nowrap, which is to say the default was the one nobody wanted. A long label now keeps the button one line tall and makes it wider instead.

  • .btn-toolbar spaces its groups on its own with a .5rem gap (--cui-spacer-3). Drop the me-* utilities that carried the spacing in v5, or they now add to the gap.

    It is still a token, so the old behaviour is one declaration away — on a single button, on a theme, or globally:

    .btn-that-wraps { --cui-btn-white-space: normal; }
:root { --cui-btn-white-space: normal; }

    In Sass, $btn-white-space: normal. The token is declared on .btn itself, so an override has to reach the button — setting it on an ancestor is not enough.

    Look at rows that hold several buttons: a flex row without .flex-wrap grows wider now instead of taller, so add it where the group should break onto a second line rather than push the layout out.

  • .btn-icon (new). A button that holds nothing but an icon: no padding, and its width follows its height, so it stays square at every size.

  • A variant is a shape, the colour is a theme. .btn-solid, .btn-outline, .btn-subtle (new) and .btn-ghost take their colour from a .theme-* class on the button or on any element above it, and each carries the base button styles on its own — .btn is no longer required next to them:

    - <button class="btn btn-primary">Save</button>
+ <button class="btn-solid theme-primary">Save</button>

    The colour classes keep working and stay the spelling the docs use: .btn-primary is .btn-solid.theme-primary, .btn-outline-primary is .btn-outline.theme-primary, and .btn-subtle-* completes the set. What changes is that one rule per variant now serves every colour, so a theme colour of your own gets the whole set for free.

  • Breaking A bare .btn is a neutral button, not an invisible one. It renders in the surface colours (--cui-bg-2, one step darker on hover) instead of being transparent and unstyled. Buttons that carry a variant or a colour class are unaffected. For the old behaviour use .btn-ghost, which is transparent by design.

  • .btn-xs (new). A fourth size below .btn-sm, reading the shared --cui-btn-input-xs-* tokens.

  • The resting button shadow is gone. $btn-box-shadow and --cui-btn-box-shadow are removed; a .btn draws no box-shadow at rest even with $enable-shadows: true, only the pressed state keeps its inset (--cui-btn-active-shadow). The removed default was the v4 bevel (inset 0 1px 0 rgba(white, .15), 0 1px 1px rgba(black, .075)); put it back with your own .btn { box-shadow: … } if you want it.

Loading button

  • Breaking disabledOnLoading no longer sets the disabled attribute. A disabled button drops focus, so a keyboard or screen reader user who pressed it landed on the page body. While loading, the button now gets aria-disabled="true" and .disabled, keeps focus, and ignores clicks and form submission until it stops. CSS or scripts that read :disabled on a loading button should read [aria-disabled="true"] instead.
  • The start and the end of loading are announced when the button has focus: its name followed by the new ariaLoadingLabel option, then its name again. While loading, the spinner is a role="img" named by ariaLoadingLabel instead of an empty role="status".

Navbar

  • Breaking .navbar-expand-* reads the navbar’s own width, not the viewport’s. Every .navbar is a query container now, so a navbar in a sidebar or a narrow dashboard column collapses there while a full-width one on the same page stays expanded. For a navbar that spans the page — which is most of them — nothing changes, because its width is the viewport’s.
  • flex-wrap: nowrap and justify-content: flex-start moved from .navbar-expand-* onto its inner .container*. A container query styles descendants of the container, never the container itself, and the inner container is where those two properties took effect anyway (the navbar’s children inherit flex-wrap). A navbar written without an inner .container, .container-fluid or .container-{breakpoint} no longer gets them — wrap its content, the way every example in these docs does.
  • --cui-navbar-text-padding-y and --cui-navbar-toggler-icon-size are new. The padding that lines .navbar-text up with the nav links, and the size of the hamburger glyph, were both compiled into their rules. The padding could not be matched from outside at all: the value it pairs with, --cui-nav-link-padding-y, is declared on .navbar-nav, which is .navbar-text’s sibling and therefore invisible to it. Both are declared on .navbar now, at their current values.
  • An expanded navbar flattens a .drawer, not just an .offcanvas. The reset that turns the collapsed panel back into an inline nav named .offcanvas only, so a .drawer inside a .navbar-expand-* stayed a fixed side panel over the page at every width — measured at 400×868 next to the offcanvas’s 1176×24. Both are handled now.
  • Breaking Three navbar defaults move. .navbar takes --cui-navbar-min-height: 3.5rem, so a navbar with short content no longer collapses below the height of one with a brand in it. .navbar-brand takes --cui-navbar-brand-font-weight, defaulting to medium rather than the body weight. .navbar-nav takes --cui-nav-gap, a .25rem gap between links that the link padding used to carry alone. Set any of the three to its old value to keep the previous rendering.
  • .navbar-translucent is new. It tints and blurs the navbar the way .toast-translucent does for a toast, mixing --cui-navbar-bg — a new token, defaulting to the body background — at --cui-translucent-opacity.
  • A theme beats a navbar token, as everywhere else. --cui-navbar-brand-color, -brand-hover-color and -active-color carried the --cui-theme-* slot inside their own default, so setting one of them inside a .theme-{color} navbar dropped the theme. The slot sits on the property now, so the theme wins — the same order every other component follows.

Checkbox, radio and switch: the class moved onto the input

Breaking

.check, .radio and .switch go on the <input> itself. There is no wrapper and no second element: appearance: none lets the control render a pseudo-element, so the mark is drawn on the input, and its colour is a token (--cui-check-mark-color) rather than a value baked into an SVG. The separate dark-mode switch artwork is gone with it — a thumb painted from a token follows the colour scheme by itself.

- <div class="form-check">
-   <input class="form-check-input" type="checkbox" id="c">
-   <label class="form-check-label" for="c">Label</label>
- </div>
+ <div class="form-field">
+   <input class="check" type="checkbox" id="c">
+   <label for="c">Label</label>
+ </div>

The v5 spelling still works. .form-check, .form-check-input, .form-check-label, .form-switch and .form-check-inline are kept as a compatibility layer — aliases of the new controls, not a second implementation, so there is one engine to maintain and the old markup lays out exactly as it did. Verified by measuring geometry across six markup variants and eight dimensions each: zero differences. It is deprecated in v6 and removed in v7. It ships in coreui-legacy.css, not in coreui.css, so a build whose markup has moved leaves the sheet out and carries no .form-check* selector at all.

.btn-check on the <label> is a current feature and lives with the buttons. The v5 spelling — .btn-check on the <input>, with a sibling <label class="btn"> — is in coreui-legacy.css alongside the rest.

The wrapper it draws is styled from scss/_legacy.scss and goes when the layer does.

Five Sass variables shaped the old artwork and cannot be honoured any more, because the compatibility layer draws through the new engine: $form-check-input-checked-bg-image, $form-check-radio-checked-bg-image, $form-check-input-indeterminate-bg-image and $form-check-transition. Their replacements are --cui-check-mark-checked, --cui-radio-mark, --cui-check-mark-indeterminate and the controls’ own transition tokens. $form-check-label-color and -cursor keep working. $form-check-btn-check-disabled-opacity goes with the toggle button’s move to the buttons — it duplicated $btn-disabled-opacity, which is now what the disabled toggle reads, through --cui-btn-disabled-opacity.

Removed .form-check-reverse is gone. It right-flushed the label and the control as a pair — which order utilities express directly — and it was never the settings row (label on the left, control on the right) that people actually reach for; that one is justify-content: space-between. The React and Vue reverse prop still emits the class and therefore stops having an effect; it is retired with those components in the framework editions.

.form-check-labela plain <label>

The switch is sized by one token, and gains .switch-sm. --cui-switch-width is derived from --cui-switch-height through the new $switch-aspect-ratio — a plain number, multiplied in the browser — so a size sets the height alone. The size classes now scale the label as well, matching .check-sm / .radio-lg. $switch-sizes replaces the width/height pairs, and the deprecated .form-switch-lg / -xl read it too — $form-switch-widths is gone. Those two classes render exactly as .switch-lg / .switch-xl now, so they grow a little: the track was 1.25em / 1.5em tall on a 2:1 ratio, and is 1.5rem / 1.75rem on the library’s 1.75 ratio.

Fixed: the switch animates again. --cui-switch-transition carried a property name inside it (background-position .15s ease-in-out, inherited from v5’s $form-switch-transition), so transition: inset-inline-start var(…) resolved to something invalid and every switch transition was dropped. It is two tokens now — --cui-switch-transition-duration and -timing — and the thumb slides rather than the background position.

Breaking The switch is redrawn. The track is 1.25rem tall with a 1.75 aspect ratio (was a 2:1, font-relative em track), pill-radiused, on the tertiary surface with an inset shadow; the thumb is white with a drop shadow and turns contrast-coloured when checked. A disabled unchecked switch swaps to the disabled surface with a faded thumb instead of dimming wholesale; a checked one dims. --cui-switch-border splits into -border-width and -border-color, and $form-switch-color, $form-switch-width and $form-switch-border-radius fed only the old look and are removed. The deprecated .form-switch-lg / -xl are redrawn with the rest.

The controls animate on shared knobs. :root carries --cui-control-transition-duration and -timing (an overshoot easing); the checkbox tick and the radio dot pop in on them, the boxes’ colours animate, and the switch thumb slides on the same pair — the three controls move in sync and restyle from one place. Reduced motion disables all of it as usual.

New: checkbox and radio have sizes. .check-sm / .check-lg and .radio-sm / .radio-lg — v5 had none, only the switch was sizeable. Each sets one custom property; the mark scales with the box and the alignment margin is computed from the same value, so any size you set yourself stays on the text’s optical centre too.

Multi Select’s option indicators moved with it — they render as a decorative .check now, so a build with the compatibility layer off still draws them.

Checkbox, radio and switch: one page became four

  • Each control now owns its custom properties. --cui-checkbox-*, --cui-radio-* and --cui-switch-* feed the shared implementation at runtime, so restyling checkboxes no longer drags radios along and no longer needs a Sass rebuild. Set them on the control — a token an element declares for itself cannot be overridden from an ancestor. The old --cui-form-check-* properties still exist and still work; they are the shared layer underneath.

  • The control stays on the text baseline when you resize it. Its margin-top used to be Sass arithmetic over $form-check-input-width, so changing the width token at runtime moved the box off the line. It is a calc() over the size token now.

  • Sized switches are token overrides. .form-switch-lg / -xl set --cui-switch-width and --cui-switch-height instead of writing their own geometry, so a size the map does not name is two custom properties rather than a Sass recompile.

  • The Sass variables behind all of this moved into scss/forms/_checkbox.scss, _radio.scss and _switch.scss. $form-check-* and $form-switch-* keep working — the new per-control variables default to them.

  • The docs split. /forms/checks-radios/ is now Checkbox, Radio and Switch — one page per control, each self-contained down to its own toggle-button and Sass sections. The old URL redirects to Checkbox. No classes changed: .form-check, .form-check-input, .form-check-label, .form-switch and .form-check-inline all work exactly as before; .form-check-reverse is removed.

  • New: .form-field, a grid wrapper that lays a control out with its label, description and validation feedback on one consistent gap, so a form is spaced by the field instead of by margin utilities on its parts. A bare .form-check-input (one written without its .form-check wrapper) switches the field to a two-column layout through :has().

Stacks

  • New: .hstack{-sm|-md|-lg|-xl|-2xl} and .vstack{-sm|-md|-lg|-xl|-2xl} switch direction at a breakpoint. The breakpoint is the width of the nearest query container, so mark an ancestor with the new .stack-container (or the .contains-inline utility) — without one the direction never switches. Plain .hstack and .vstack are unchanged, including .hstack’s vertical centring and its shrink-to-content width.

Images and figures

  • --cui-thumbnail-* and --cui-figure-caption-* are declared, not just read. They existed only as the fallback arm of a var() call, so nothing reported them and an override had to guess the name. .img-thumbnail and .figure-caption declare their full set on the element, padding, border width and caption font size included.
  • --cui-figure-img-margin-bottom is new. The gap between a figure’s image and its caption was compiled into the rule, so the only way to change it was to rebuild from Sass. .figure-img declares it now, and it is the one figure measurement you can retune in the browser.

Figures

  • Breaking .figure is an inline flex column and spaces its parts with --cui-figure-gap. $figure-img-margin-bottom and --cui-figure-img-margin-bottom are gone — the gap (knob: $figure-gap, same .5rem) replaces the image’s bottom margin, and .figure-img carries no styles at all any more — keep it in your markup or drop it, both render the same. Documented markup renders pixel-identically; an <img> without width/height attributes can now stretch to a wider caption (flex stretch), so give figure images explicit dimensions — which they need anyway to avoid layout shift.

Reboot

  • Links change color on hover. --cui-link-hover-color was declared and read by navs and pagination, but a plain <a> only ever changed its underline. It now switches color as well, and inside a themed surface it hovers to --cui-theme-fg-emphasis.
  • The underline sits .2em below the text. <a> reads the new --cui-link-underline-offset token (knob: $link-underline-offset), so underlines clear descenders instead of cutting through them. The .underline-offset-* utilities and .icon-link still override it per element; set the token to auto for the old browser default.
  • accent-color: var(--cui-primary) on :root. Native controls we don’t restyle — a bare checkbox, radio, range or <progress> — follow the brand color instead of the browser’s blue.
  • Every segment of a date or time input gets its padding removed. The list covered five pseudo-elements and one of them (::-webkit-datetime-edit-minute) had been renamed by browsers years ago; seconds, milliseconds, the week number and the AM/PM field were never in it. <input type="time" step="1"> no longer renders taller than a text input.
  • tel, url, email and number inputs stay LTR everywhere. The rule was scoped to [dir="rtl"] elements, so it missed pages that set the direction on <html> through the language rather than the attribute.
  • pre reserves scrollbar space (scrollbar-gutter: stable), so a horizontal scrollbar no longer covers the last line of a code block.
  • Reboot’s type and spacing are CSS variables on :root. Heading margin, family, style, weight and line height, paragraph margin, hr, legend, dt, sub/sup, mark padding, the code font size and --cui-list-padding-x are declared rather than compiled in, so a subtree can be retyped without a class. <kbd> carries its own set on the element, --cui-kbd-border-radius included.
  • .h1–.h6, .small, .mark and .initialism are defined in Reboot, next to the elements they mirror, instead of @extend-ing them from _type.scss. Only .initialism changes cascade layer (content → reboot); the others were already emitted there, because @extend hoists a class to wherever the extended selector is defined. _type.scss is gone with .lead and .display-* (see the type scale below).
  • Hardcoded spacing in Reboot now reads the --cui-spacer-* scale (address, ol/ul/dl, dd, blockquote, pre, figure). Values are unchanged.

Floating labels

  • The label may now come first. .form-floating matches the control’s state in both directions — forward from the label with :has(), backward from the control with ~ — so <label> before the control floats and disables exactly like the v5 order, which keeps working. Writing the label first lets a screen reader announce it before the field’s value, and the docs examples do.
  • A textarea’s label stays at the top. The label is a flex box centred on the control, and label:has(~ textarea) anchors it to the start instead, so it floats correctly however tall the textarea is.
  • Breaking The placeholder shows once the field has focus. It used to stay transparent in every state; it now appears under the floated label while the field, or the control inside a field component, has focus, and stays hidden while the label rests in the field. A read-only .form-control-plaintext keeps it hidden.
  • New: .form-floating-always keeps the label floated and the placeholder showing while the field is empty. It works on .form-floating or on any ancestor. See Always floating.

Lists

  • --cui-list-inline-padding is new. The gap between .list-inline-items was compiled into the rule, so respacing an inline list meant rebuilding from Sass. .list-inline declares it, at the same .5rem.

Tables

  • .table-responsive* is a query container. It still scrolls horizontally below its breakpoint; the addition is that things inside it can now respond to its width.
  • New: .table-stacked{-sm|-md|-lg|-xl|-2xl} turns rows into stacked blocks below the breakpoint, reading the width from the .table-responsive* wrapper. Give every <td> past the first a data-cell attribute for its label; the header is hidden visually and kept in the accessibility tree. See Stacked tables.
  • New: .table-card wraps a table in a card’s border and corner radius, clips the cells, and drops the table’s bottom margin and the borders that would stack on the frame. It goes around the table or on its .table-responsive* wrapper. See Card-like tables.
  • Cell padding, vertical alignment and the border width are CSS variables now. --cui-table-cell-padding-y, --cui-table-cell-padding-x, --cui-table-cell-vertical-align, --cui-table-border-width and --cui-table-group-separator-color are declared on .table instead of being compiled into the cell rule. This also fixes stacked tables, which read --cui-table-cell-padding-* and --cui-table-border-width while nothing declared them, so their rows collapsed to zero padding and lost the separating line.
  • .table-sm sets the padding variables on the table instead of overriding the padding on every cell. Anything that raised specificity to beat .table-sm > :not(caption) > * > * can set --cui-table-cell-padding-y/-x instead.
  • Breaking The contrast factors are percentages. $table-striped-bg-factor, $table-active-bg-factor and $table-hover-bg-factor changed from unit-less fractions (.05) to percentages (5%), because they now ship as the --cui-table-*-bg-factor variables that color-mix() reads at runtime.
  • The state colours follow --cui-table-color. --cui-table-striped-color, --cui-table-active-color and --cui-table-hover-color default to var(--cui-table-color), and the matching backgrounds are mixed from it, so a variant only has to set --cui-table-color, --cui-table-bg and --cui-table-border-color.

Blockquote

  • Breaking The source line reads --cui-secondary-color. .blockquote-footer was painted with --cui-gray-600, a fixed value that never flipped with the colour mode: 4.15:1 on the light background and 3.65:1 on the dark one, both under the 4.5:1 minimum. The secondary colour is defined per mode and clears the threshold in both.
  • The quote lays its children out with flex and gap. Spacing inside a multi-paragraph quote is --cui-blockquote-gap rather than each paragraph’s own bottom margin, and .blockquote > :last-child { margin-bottom: 0 } is gone with the margins it existed to cancel.
  • The footer no longer pulls itself up with a negative margin. A quote followed by .blockquote-footer drops its own bottom margin instead (:has()), so the two spacings can be set independently: --cui-blockquote-margin-y and --cui-blockquote-footer-margin-y.

Toast

  • New: Toaster creates toasts from options and keeps them in a store keyed by id — add() returns the id (an existing id updates in place, a closing one is replaced), update() rewrites a toast, close() hides one or all, promise() follows an asynchronous operation through loading, success and error. It creates its own .toast-container placed by placement, caps visible toasts with limit (the oldest stay in the DOM, inert and hidden), announces each toast through announce() by priority and can render an action button. Toasts slide in from beyond the container’s edge and back out, toasts over the limit fade out instead of vanishing, and the toaster glides the remaining toasts into place when one leaves; stack: true piles them up, newest in front, and spreads them on hover or focus. Nine .toast-container-{block}-{inline} classes pin a container to the viewport in place of the position-fixed top-0 end-0 utility stacks. New classes: .toast-title, .toast-description, .toast-action.
  • Breaking The fade moved to CSS. Toast was the last component driving its animation from JavaScript — it toggled .fade, forced a reflow, then juggled .show, .showing and a deprecated .hide class to fake an exit. Menu and the picker popup already express this with @starting-style and a discrete display transition, and Toast now does the same. JavaScript only toggles .show.
    • The animation option and data-coreui-animation are gone. Add .toast-instant to skip the animation.
    • .showing and the deprecated .hide class are gone, and toasts no longer get the generic .fade class. Replace any CSS or tests that depend on them.
    • The transition is tuned with --cui-toast-transition-duration and --cui-toast-transition-timing.
    • isShown() returns false as soon as hide() is called, rather than when the fade-out ends.
  • Breaking Toasts are opaque by default. --cui-toast-bg and --cui-toast-header-bg resolved to color-mix(in srgb, var(--cui-body-bg) 85%, transparent), so every toast let 15% of whatever sat behind it through — with no blur to settle it, text underneath read straight through the message. Both now resolve to var(--cui-body-bg). Add .toast-translucent for the see-through look, which puts blur(5px) saturate(180%) behind the toast and thins the header to match, the same way .card-translucent and .menu-translucent work.
  • New: .toast-container-{top|middle|bottom}-{start|center|end}. Nine classes pin a .toast-container to the viewport (position: fixed), inset from the edge by --cui-toast-container-inset (--cui-spacer-5, 1rem, by default) and centred with logical insets and auto margins rather than transforms, so they hold in RTL. They replace the position-fixed top-0 end-0 p-3 utility stack; inside a positioned box add .position-absolute to pin the container to the box. --cui-toast-container-inset is declared on .toast-container next to --cui-toast-zindex.

Card

  • Breaking A card is roomier and framed in the solid border colour. --cui-card-spacer-y / -x go from 1rem to --cui-spacer-6 (1.25rem), and the image-overlay padding follows them. The header, the footer and a list group placed directly in the card take --cui-card-spacer-x as their inline padding, so their text lines up with the body; the header and footer keep .5rem of block padding. The border reads --cui-border-color instead of --cui-border-color-translucent, except on .card-translucent, and the radius is --cui-radius-7 (see the radius scale below). A card filled with .text-bg-* keeps that neutral frame; add the matching .border-{color} to frame it in the fill colour. To keep the v5 spacing, set --cui-card-spacer-y and -x to var(--cui-spacer-5) on .card.
  • Breaking .card-header-pills is gone. It only pulled the pill row out to the header’s padding edge, which is wrong for pills — they carry their own background, so flush against the header’s inner edge they touch the border. Drop the class and keep .nav.nav-pills.
  • The footer follows the theme colour like the header does. A themed card (.card.theme-inverse, say) used to paint the footer’s background from the theme while leaving its text at the body colour, so the label sank into the fill. The footer now reads --cui-theme-contrast with --cui-card-cap-color as the fallback, the same expression the header already used.
  • Every card token now carries a real value. --cui-card-title-color, --cui-card-subtitle-color, --cui-card-cap-color, --cui-card-color, --cui-card-height and --cui-card-box-shadow shipped as empty declarations (--cui-card-title-color: ;), because their Sass variables were null and interpolating null yields an empty string rather than dropping the entry. An empty custom property makes every var() that reads it invalid at computed-value time, so the rendered result happened to be right, but the token read as blank in devtools and could not be told apart from one you had cleared yourself. They now ship inherit, auto and none, which compute to the same thing and make the customization surface inspectable.
  • The last card in a .card-group gets its bottom-left corner squared. The rule targeting it was written > card-footer, without the leading dot, so it matched an element type that does not exist and never applied.
  • A theme class works on a single section, not just the whole card. <div class="card-header theme-primary"> used to paint white text on a neutral header, because the background came from --cui-card-cap-bg, a token declared on .card — a custom property resolves where it is declared, and --cui-theme-base was set one level below it, on the header. The theme indirection moved to the point of use, so each section reads the theme in its own scope. A theme class on the .card itself behaves exactly as before.
  • Breaking .card-body is a flex column. It spaces its children with --cui-card-body-gap and zeroes their block margins, so nothing in a card needs .mb-* to sit correctly any more. Two consequences for existing markup: a direct child takes its natural width rather than filling the card (add .w-100 where a block child has to stretch), and text-align no longer moves a button or a link, because they are flex items — use .mx-auto or .ms-auto instead.
  • Stacked sections are divided by a single rule. A body, a list group or a bottom image cap that follows an image cap, a body or a list group draws a divider above itself in the card’s own border, so two bodies in a row, or an image cap above a body, no longer sit with nothing between them, and a border utility or a theme on the card carries over to every divider. A section hidden with hidden or .d-none does not count. A header and a footer draw their own divider, as before.
  • .card-group squares the corners at each seam along the writing direction. The rules named the physical corners, so a right-to-left group squared its outer corners and rounded the ones that meet. A list group at the edge of a grouped card is squared like the other sections.
  • Breaking .card-link is gone, along with --cui-card-title-spacer-y. Both existed to space children the gap now handles; the class’s inline margin only ever worked because the links were inline. Wrap them yourself: <div class="hstack gap-4">…</div>.
  • New: .card-row lays a card out along the inline axis, with .card-img-start and .card-img-end for an image cap on either side. It replaces the .row.g-0 + .col-md-* recipe, which needed a wrapper per section and drew no divider between them.
  • New: .card-subtle swaps the theme’s solid fill for its subtle background, border and emphasis text.
  • New: .card-translucent blurs and saturates whatever is behind the card and thins out the caps to match. The mix and the filter are the shared --cui-translucent-* tokens; the caps read --cui-card-translucent-cap-bg-opacity (Sass default $card-translucent-cap-bg-opacity).
  • Breaking .card-group attaches its cards from a container query, not a media query. The sm breakpoint is now the width of the nearest query container, which is what a group inside a column actually has to fit — the viewport being wide never meant the group was. Mark an ancestor with .contains-inline; without a container the query has nothing to read and the cards stay stacked at every width.

List group

  • Breaking .list-group-horizontal-{sm|md|lg|xl|2xl} turns horizontal from a container query. Same change and same fix as .card-group: put .contains-inline on an ancestor, or the list stays vertical. Plain .list-group-horizontal is unconditional and needs no container.
  • An active item under a .theme-* class is filled, like a page link. .list-group-item.active reads --cui-theme-contrast for its text and --cui-theme-bg for its background and border — the same slots the pagination, the badge and the button use — so the active item of a .theme-danger list is the same red as the active page of a .theme-danger pagination. A pressed action (:active) reads --cui-theme-bg-muted, like hover. Without a theme class nothing changes.

Tab

  • Breaking A tab pane fades on its own — .fade on a .tab-pane does nothing for it. .tab-pane carries the transition and --cui-tab-pane-transition-property / -duration / -timing, and @starting-style supplies the state to fade from. Drop .fade from your panes; add .tab-pane-instant to a pane that should switch without one. .fade itself stays as a generic helper for your own markup.

  • The pane no longer waits a full transition before it starts fading. The JS added .show from inside the callback it had queued on the pane’s own transition — so it waited out a fade that had not begun, then began it. Both classes land in the same frame now, and shown waits on the pane, the element that actually animates, instead of the tab button, which only transitions its colours.

Modal

  • Breaking A size modifier applies at every viewport. .modal-lg and .modal-xl were withheld until the lg and xl breakpoints, so on a tablet a large modal was 500 px — the same as one with no modifier at all — and an extra-large modal on a 1100 px screen was 800 px. Both ask for their width everywhere now, capped by max-width: calc(100% - margin * 2) exactly as before, which is what kept horizontal scrollbars away in the first place. At 768 px .modal-lg goes 500 → 712 px, and at 1100 px .modal-xl goes 800 → 1044 px.

  • Breaking .modal-sm is narrow on phones too. It used to fall back to the default width below the sm breakpoint, so on a 360 px screen it filled the width; it is 300 px there now. Drop the modifier for markup that should fill a small screen.

  • $modal-sizes replaces the three breakpoint blocks. Sizes come from a map and a loop, the same shape .dialog-* already used — one model for both windows instead of two.

Pagination

  • Breaking A page link is sized from the shared control scale. Pagination kept its own padding values, so .pagination-lg did not match .btn-lg or .form-control-lg — it measured 56 px against their 48. The tokens read --cui-btn-input-* now, .page-link is a centred flex box with --cui-pagination-min-height, and all three sizes line up. The base and small sizes are unchanged; the large one loses 8 px of height and some horizontal padding.

  • Breaking pagination-size() is removed, together with $pagination-padding-{x|y}-{sm|lg} and $pagination-border-radius-{sm|lg}. Sizes are generated by a loop over $pagination-sizes; add an entry to it and define the matching --cui-btn-input-<size>-* values instead of calling the mixin.

  • Keyboard focus keeps the theme colours. :focus-visible read --cui-pagination-focus-color and -focus-bg with no theme slot, so tabbing to a link inside .theme-success dropped it back to the plain link colour. Both now read --cui-theme-fg-emphasis / --cui-theme-bg-subtle first, like every neighbouring state.

  • $pagination-margin-start is removed. The overlap between links is calc(-1 * var(--cui-pagination-border-width)), so it follows a border width changed at runtime instead of the value frozen at build time. The Sass conditional that compared the variable against that expression is gone with it.

Placeholder

  • The opacities are CSS variables. --cui-placeholder-opacity-max and --cui-placeholder-opacity-min on .placeholder set the resting opacity and the pulse, and --cui-placeholder-wave-opacity-max and -min on .placeholder-wave set its highlight, so both can be retuned on an instance. They were compiled in from $placeholder-opacity-max and -min.
  • Placeholders are paler, taller and rounded. The resting opacity is .18 (was .5) and the pulse dips to .1 (was .2). The default height is 1.25em (was 1em), capped a quarter em below the line height so a placeholder never makes a heading or a tight line taller; .placeholder-xs is .75em (was .6em), .placeholder-sm 1em (was .8em) and .placeholder-lg 1.75em (was 1.2em). Each placeholder has a --cui-radius-3 corner. A button, avatar, badge or chip that takes .placeholder as a modifier keeps its own height and corners.
  • .placeholder-wave is a sweeping highlight and the recommended loading animation. A narrow bright band crosses the placeholders every 1.6s instead of a wide gradient every 2s, and it also works on text. The opacity pulse is .placeholder-pulse now; .placeholder-glow stays as its alias. The keyframes are renamed with it, so custom CSS that names animation: placeholder-glow needs placeholder-pulse. With reduced motion the wave stops and drops its mask.

Popover and Tooltip

  • Deprecated placement takes the logical start and end; left and right are deprecated. The physical names never meant a physical side — both components have always mirrored them in RTL, which their own pages documented — so right was already “the end of the reading direction” wearing the wrong name. The new spellings say it, and match the ones Menu and Dropdown already take. Nothing breaks: left and right keep working and resolve identically, and they are removed in v7.

  • The fade moved to CSS. Neither component renders the fade helper class any more; .show alone drives the transition, with @starting-style supplying the state to animate from. animation: false renders .popover-instant / .tooltip-instant instead of omitting fade, and a custom template opts out with the same class. The option itself is unchanged; only custom CSS targeting .popover.fade or .tooltip.fade needs updating. Tune the motion with --cui-popover-transition-duration / -timing and their tooltip counterparts.

  • A bottom-placed popover’s arrow is filled like the header it points into. The arrow sits above the header and was drawn in the body background, so it read as a notch cut out of the header strip. It takes --cui-popover-header-bg when a header follows it, and stays on --cui-popover-bg when there is none.

  • --cui-popover-header-color reads --cui-heading-color. It resolved $headings-color at build time, so a runtime override of the heading colour skipped the popover header. The default is unchanged.

Progress

  • Breaking $progress-bar-animation-timing is replaced by $progress-bar-animation, which carries the keyframes name too. The stripe animation is a CSS variable now — --cui-progress-bar-animation — so its speed, easing and keyframes can be changed on an instance instead of only at build time. A Sass override that passed just the timing (1s linear infinite) has to pass the whole shorthand (progress-bar-stripes 1s linear infinite).

  • The label font size follows --cui-font-size-sm. It was three quarters of the body font size, a value only this component used; it is the shared small size now, which makes it one step larger. Set --cui-progress-font-size to go back.

  • Breaking .progress-group, .progress-group-prepend, .progress-group-header and .progress-group-bars are removed. Four classes carried a flex row, a 100 px label column, a header row and a 2 px gap between bars — all of which utilities already do. Use .hstack / .vstack with a gap-* and put the label column’s width in a style, as the Grouping bars examples now show.

  • Breaking .progress-thin is removed. It did nothing an inline height does not. Use style="height: 4px" on the .progress, as the Height section shows, or set --cui-progress-height if you want the stripe geometry to follow the height too.

  • .progress-white sets tokens. It was painting background-color past --cui-progress-bg, so nothing could adjust it. It now sets --cui-progress-bg (translucent white) and --cui-progress-bar-bg (--cui-white) and lets the base rules paint; the bar stays white under a .theme-* class, as the variant is meant for dark and brand-coloured surfaces.

  • Gradient bars. --cui-progress-bar-bg-image (default none) paints the bar with an image on top of its colour, so a gradient is one variable on the .progress or the bar. The stripes moved to their own tokens for the same reason: --cui-progress-bar-stripes holds the pattern and --cui-progress-bar-stripe-color its colour, and .progress-bar-striped layers the pattern over the image. The progress-bar-stripes keyframes now shift only the first background layer, so the image underneath stays put.

  • .progress-segmented. A mask that cuts a .progress or .progress-stacked into a row of rounded segments, --cui-progress-segment-min-width wide and --cui-progress-segment-gap apart — or exactly --cui-progress-segments of them when that is set — with corners from --cui-progress-segment-border-radius (--cui-radius-2 by default, 0px for square). Everything under the mask — transition, theme, gradient, stripes — behaves as before.

  • New Progress plugin. Initialized on every .progress-segmented, it reads the bar’s aria-valuenow, aria-valuemin and aria-valuemax and sets --cui-progress-segments-filled, which the stylesheet turns into the bar’s width, so the fill ends on a whole segment. It also counts how many segments of --cui-progress-segment-min-width fit the track, capped at --cui-progress-segments when set, and follows the track as it resizes; a script that changes the bar’s aria-valuenow, aria-valuemin or aria-valuemax calls update(). An inline width on the bar still wins over the segment fill. coreui.Progress is exported next to the other plugins.

Spinner

  • Breaking Spinners are sized in em, not rem. .spinner-border and .spinner-grow are now 1em square with a .125em border, so a spinner takes the font size of whatever it sits in instead of being a fixed 32 px block. Inside a button or a paragraph it lands at the size you previously had to ask for with a modifier; standalone it is half of what it was. Set --cui-spinner-width / -height, or the $spinner-width / $spinner-height Sass variables, to go back to a fixed size.

  • Breaking .spinner-border-sm and .spinner-grow-sm are replaced by one .spinner-sm. The small variant no longer has to correct the border width, so a single class serves both spinners.

  • Breaking --cui-spinner-vertical-align is gone. Spinners are inline-flex and assume a flex parent; the -.125em baseline nudge it used to need no longer applies.

  • The animation timing function is a token. .spinner-border keeps linear, while .spinner-grow now eases with ease-in-out instead of pulsing linearly. Override --cui-spinner-animation-timing-function to change either.

  • .spinner-rotate is new. It applies only the rotation, so you can spin your own SVG or icon without inheriting the bordered circle.

  • .btn-loading sizes its spinner from the button. LoadingButton no longer adds a -sm class to the spinner it injects; the spinner follows the button’s font size, so it now scales with .btn-sm and .btn-lg.

Footer

  • Breaking .footer is gone. Every declaration it carried is reachable with utilities, so <footer class="footer"> becomes <footer class="d-flex flex-wrap align-items-center justify-content-between bg-3 border-top px-5 py-3">. The only property without a utility is min-height: 3rem; where a floor matters, set it yourself or pad with py-4. The --cui-footer-* variables and the $footer-* Sass variables go with it.

  • Breaking .footer-sticky is replaced by .sticky-bottom. It pins to the bottom the same way but sits on --cui-z-sticky rather than --cui-z-fixed, so a footer that has to stack above fixed chrome needs its own z-index.

  • Breaking .footer-fixed is replaced by .fixed-bottom. It pins to the bottom of the viewport the same way and, unlike the footer class, is available in both editions.

Header

  • Breaking .header-sticky is replaced by .sticky-top. The two rules were identical — position: sticky, top: 0, --cui-z-sticky — so the utility pins the header exactly as the component class did, and it composes with the responsive variants (.sticky-md-top) the component class never had.

  • .header-fixed never existed. The position property on the framework components accepted fixed and rendered a class the stylesheet did not define, so it did nothing. Use .fixed-top or .fixed-bottom; on the framework components, position renders those utilities now.

  • .prevent-hide on .header-toggler is removed. It forced display: block !important against a hide rule that no longer exists; nothing in the library or the admin templates sets the class.

Callout

  • The callout takes its colour from a .theme-* class, on the callout or on any element above it, like the alert does. The class colours the leading edge and tints the border, and because it exposes every slot, .theme-subtle next to it fills the callout without naming the colour twice.
  • Deprecated .callout-{color} still works and is removed in v7. Each modifier is generated from $theme-colors through the same theme-tokens() mixin as the theme class, so .callout-primary is .callout.theme-primary.
  • Breaking $callout-variants is gone. The modifier classes are generated from $theme-colors, so adding a theme colour adds its callout class — there is no separate map to keep in step.
  • A callout without a colour no longer draws its leading edge in currentColor. --cui-callout-border-left-color was read but never declared: only the modifiers set it, so the declaration was invalid on a bare .callout and the property fell back to its initial value. It now defaults to the callout’s own border colour.
  • The 1px border of a coloured callout is tinted. It reads --cui-theme-border where it used to stay neutral, so a coloured callout is a coherent block rather than a grey box with a coloured tick. The leading edge is unchanged.

The deprecated colour classes are a separate stylesheet

  • .alert-{color}, .btn-{color}, .btn-outline-{color}, .btn-subtle-{color}, .btn-ghost-{color}, .callout-{color}, .chip-{color} and .list-group-item-{color} ship in coreui-legacy.css. Load it after coreui.css and they render exactly as before; leave it out once your markup uses the theme classes. They are removed outright in v7.
  • The buttons carry the colour spelling in two places, not one. Besides the loop that points each class at a theme colour, a variant’s base declarations are repeated for the colour classes — the legacy sheet carries both, so .btn-primary moves whole rather than surviving as a rule with no colour.
  • alert-modifiers and btn-variant-loops each covered two loops, one deprecated and one not. They are split, so the docs can mark the deprecated half without mislabelling the other: the alert variants loop is alert-variant-loop, and the deprecated button classes are btn-deprecated-modifiers.

Helpers

  • .link-{color} is gone; a theme class colours a link. Reboot resolves a link’s colour from --cui-theme-fg, which every .theme-* class sets, so the colour follows the theme instead of needing its own class:

    <!-- v5 -->
<a href="#" class="link-primary underline-opacity-25">Primary link</a>

<!-- v6 -->
<a href="#" class="theme-primary underline underline-opacity-25">Primary link</a>

    Two things change beyond the class name. The theme slot is a tone picked for text rather than the raw brand colour — it darkens on a light background and lightens on a dark one, where .link-* gave the same colour in both, so the link is more readable in dark mode and slightly different in light. And the underline needs .underline to carry it; its colour now defaults to currentColor, so it follows the theme unless you name one with .underline-{color}.

    .link-body-emphasis becomes .text-body-emphasis.

    The removed classes also computed their :hover colour in Sass, which froze it at build time — overriding --cui-primary at runtime never reached the hover state. The theme slots are tokens, so it does.

  • .ratio is now a native aspect-ratio utility. The helper built its ratio from a ::before with a percentage padding-top, which required a wrapper and absolutely positioned its only child. The class names are unchanged — .ratio-1x1, .ratio-4x3, .ratio-16x9, .ratio-21x9 — but they now set the CSS aspect-ratio property on the element itself.

    <!-- v5 -->
<div class="ratio ratio-16x9">
  <iframe src="..."></iframe>
</div>

<!-- v6 -->
<iframe class="w-100 ratio-16x9" src="..."></iframe>

    The wrapper and the bare .ratio class are gone; put the ratio class on the element you want sized. A custom ratio moves from a percentage to a ratio: --cui-aspect-ratio: 50% becomes --cui-ratio: 2 / 1, on .ratio-auto. The $aspect-ratios map moved from helpers/_ratio.scss to _config.scss and its values are ratios rather than percentages.

Sass architecture & design tokens

v6 adopts the Bootstrap v6 SCSS architecture: CSS cascade layers, per-component design-token maps, one shared styling surface for every text control, and runtime color math in place of precompiled shades. The global Sass knobs stay the build-time customization API, while a component’s own surface is its token map — several things below are breaking and are called out as such.

A theme class wins over a component’s own colour token

  • Breaking Under a .theme-* class the theme wins over a component colour token. A component reads the --cui-theme-* slot on the property and its own token only as the fallback. In v5 the colour came from the component’s tokens, which a modifier such as .alert-danger set, so a token you set on a coloured alert applied. In v6 a token set on a themed element, or for the whole page in your stylesheet or a $…-tokens map, changes only the components without a theme; the alert, avatar, badge, callout, chip, checkbox, radio, switch, List Box indicator, sidebar and tooltip follow the same order as the card, toast, list group and nav. To recolour one themed element, set the slot rather than the component token: <div class="alert theme-danger" style="--cui-theme-bg-subtle: …">.
  • Variant classes keep the component token as the override point. .btn-solid and the other button variants, .alert-solid, .badge-subtle, .badge-outline, .avatar-subtle and .chip-outline map the component tokens to their own slots and paint from the tokens, so on those elements a component token you set wins over the theme, as on a v5 button. Validation states (.is-invalid, .is-valid) win over a theme class too.

A numeric radius scale replaces the one global radius

  • Breaking Components read stops of a radius scale, and most got rounder. :root emits --cui-radius ($radius, .5rem by default) and the stops --cui-radius-0 through --cui-radius-9 as calc() multiples of it, plus --cui-radius-pill, and component tokens read stops instead of the one global --cui-border-radius: buttons, inputs, list groups, tabs, nav links, progress, tooltips, thumbnails, callouts, combobox options and the range slider’s tooltip sit on --cui-radius-5 (.5rem), alerts, badges, popovers, dialogs, drawers, menus, accordions, toasts, dropdowns, popups and cards on --cui-radius-7 (.75rem), and nav pills on a fixed 3rem, which keeps a pill up to 96px tall fully round and does not follow --cui-radius. Everything that used the .375rem default is visibly rounder. To keep a component on its old radius, set its own token (--cui-card-border-radius: .375rem); to retune the whole page, set --cui-radius (every stop follows) or override single stops. The $border-radius(-sm/-lg/-xl/-xxl/-pill) variables and their --cui-border-radius-* tokens are gone with it: no component read them any more (the modal, the chip, the switch, the chip input, the search button’s key, the sidebar nav, the header toggler, the password-strength segments and the validation tooltip moved to the stop with the same value: --cui-border-radius → --cui-radius-4, -sm → -3, -lg → -5, -pill → --cui-radius-pill), and the .rounded-* utilities now read the scale too (see the utilities section). --cui-border-radius is gone from :root as well: nothing in the library read it, so a stylesheet setting it changed nothing — set --cui-radius or a stop instead.

Interaction surfaces sit two rungs lighter on the ladder

  • Breaking Hover, active and disabled surfaces read lighter ladder rungs. Hover states read --cui-bg-1 (was --cui-bg-3), active and disabled states --cui-bg-2 (was --cui-bg-4), across list groups, menus, navs, pagination, breadcrumb links, the accordion’s open header, the file-input button and disabled controls; the badge’s neutral fill, the popover header, the progress track, the avatar fallback and input-group addons step down the same way. Interaction feedback is a tint rather than a block of gray — the same relationships, two rungs closer to the page. Set the component’s own token to keep a darker surface.
  • Breaking The neutral button steps down the ladder with everything else. A .btn without a theme colour rests on --cui-bg-2 (was --cui-bg-4) and hovers on --cui-bg-3 (was a hard-coded gray-300/gray-700 pair outside the ladder); the neutral subtle variant rests on --cui-bg-2 and the ghost variant’s hover wash is --cui-bg-1. The default button is visibly lighter. Set $btn-bg/$btn-hover-bg or the --cui-btn-* tokens to keep the old look.
  • Breaking The rest of the library steps down the same two rungs. The first pass left a group of components on the old surfaces; they now read the rungs their neighbours read. Hover surfaces on --cui-bg-1: the dropdown link, combobox options and the select-all row (Autocomplete, Multi Select), the control-group action button and pagination focus (was --cui-bg-4, three rungs above its own hover). The calendar cell and the time-picker roll cell, which share the date-time picker’s panel, hover one rung higher on --cui-bg-2. Rest and selected surfaces on --cui-bg-2: the active nav link and nav tab (was --cui-bg-4), the selected combobox option, the neutral chip (hovering on --cui-bg-3 instead of a mix with the foreground), the password-strength track and the search button’s key cap (active on --cui-bg-3). The range slider track sits halfway between --cui-bg-2 and --cui-bg-3 like the native range. The card header and footer read --cui-bg-1 instead of a 3 % foreground wash, so a card on a tinted parent keeps a neutral cap. The tab’s hover border reads --cui-border-subtle rather than a surface rung.
  • Foreground roles line up too. The disabled calendar cell and the disabled combobox option read --cui-fg-4 / --cui-fg-3 like every other disabled control, the weekday header and the date-input placeholder read --cui-fg-3 like every other caption and placeholder, and the active breadcrumb reads --cui-fg-1, one rung above the hovered link instead of the same one.
  • Breaking Border tokens move one rung towards the page. --cui-border-color is light-dark(gray-200, gray-700) (was gray-300 / gray-800): lighter in the light scheme, and in the dark scheme one rung further from the body, where the old value sat too close to --cui-bg-body to read as a line. --cui-border-subtle is a half step, mixed from gray-100 and gray-200 (gray-800 / gray-900 in dark) — plain gray-100 had become invisible against --cui-bg-1 on the spread-out light band. --cui-border-emphasized is gray-600 in the dark scheme (was gray-700, one rung from the plain border). Everything that reads the tokens — cards, list groups, tables, inputs, tabs, the switch and check frames — follows.

The neutral ladder is three maps

  • Breaking $theme-bgs, $theme-fgs and $theme-borders replace the neutral scalars. $fg-body, $fg-1 … $fg-4, $bg-body, $bg-1 … $bg-4, $border-subtle, $border-muted and $border-emphasized are gone; each map lives in scss/_theme.scss in the defaults() shape, :root emits every entry as --cui-bg-{key}, --cui-fg-{key} or --cui-border-{key}, and the .bg-*, .fg-* and .border-* utilities are generated from the same maps. $border-color stays a scalar — it is the default every component reads, not a rung. Override an entry instead of a variable:

+ $theme-bgs: ("body": #000);
+ $theme-fgs: ("body": #111);

    The maps also carry white, black, bg/fg (the opposite ladder’s body) and, for backgrounds, transparent, so .bg-fg, .fg-bg, .fg-white, .fg-black, .border-bg, .border-white and .border-black read tokens like every other rung. .border-body reads --cui-border-body, light-dark(gray-300, gray-800), a step heavier than --cui-border-color; it was an alias of the default border before.

Links and rules read the ladder

  • --cui-link-color is light-dark(var(--cui-primary-base), var(--cui-primary-fg)) (was the base in both schemes), so a link on the dark page reads the lighter foreground stop instead of the fill colour, and --cui-link-hover-color is a 10 % darkening of the link colour (color-mix(in oklch, var(--cui-link-color) 90%, var(--cui-black))) instead of --cui-primary-fg; override --cui-link-color and the hover follows.
  • --cui-hr-border-color is var(--cui-border-color) (was currentcolor): a rule is the same line as every other border, not a faint copy of the text colour.

Theme colours have no bare token

  • Breaking --cui-primary, --cui-secondary, --cui-success, --cui-info, --cui-warning, --cui-danger and --cui-inverse are gone. A theme colour is its set of slots — -base, -bg, -fg, -fg-emphasis, -bg-subtle, -bg-muted, -border, -focus-ring, -contrast — and the colour itself is the -base slot: --cui-primary-base is what --cui-primary was, the 100–900 scale is mixed from it, and -bg (the action background) points at it. Rename reads one to one, and set the palette stop to retint a colour:

    - .brand { color: var(--cui-primary); }
+ .brand { color: var(--cui-primary-base); }

- :root { --cui-primary: #6f42c1; }
+ :root { --cui-primary-500: #6f42c1; }

    Components that filled with the bare colour read -base now; the derived hover and active states of a .theme-* class are computed from -bg.

Breakpoints: lg 1024, xl 1280, 2xl 1536

Fixed widths and a vertical gutter knob

  • New: .w-1 … .w-12, one $spacer per step from the $sizes map, merged into the width utility next to the percentages.
  • Breaking $grid-gutter-width is $grid-gutter-x, and $grid-gutter-y joins it. make-row() takes both (make-row($gutter-x, $gutter-y)) and writes them to --cui-gutter-x / --cui-gutter-y; the row gutter defaults to 0 as before, so nothing moves unless you set it. make-grid-columns() and the card group read $grid-gutter-x. $grid-gutter-width stays as a deprecated alias of $grid-gutter-x until v7 — set the new name, the alias only reads.

The z-axis names the new components

  • New keys in $zindex-levels: menu, drawer, dialog, on the same values as dropdown, offcanvas and modal (1000, 1045, 1055). Every type stop carries its own line height

  • Breaking $font-sizes sets a line height per stop instead of one value for all headings. xs is 1.25, sm … lg the body leading (--cui-body-line-height, 1.5), xl 2.5⁄1.75, 2xl 3⁄2.25, 3xl 1.2, 4xl and 5xl 1.1, 6xl 1 — the larger the type, the tighter the leading, and the small stops read at body leading instead of 1.2. Layered shadows

  • Breaking Every shadow is a stack of two to four layers with a negative spread instead of one wide blur: a tight layer for contact, wider ones for ambient light, each at 4–9 % alpha, so a card reads as lifted rather than smeared. .shadow-xs and --cui-box-shadow-xs are new (one thin layer). The inset shadow reads 8 % in the light scheme and 26 % in the dark one. --cui-shadow-strength in the dark scheme is 2.4 (was 2.5). The knobs are unchanged: --cui-shadow-color and --cui-shadow-strength on :root, .shadow-{color} and .shadow-opacity-* on the element, $shadows in Sass — a custom entry is now a comma-separated list of layers.

Padding tokens carry both axes

  • Breaking A token that sets padding names an axis. It only restated --cui-modal-header-padding-y --cui-modal-header-padding-x, and setting it had no effect on the close button, which reads the two axes. The date picker’s ranges column and its time row also stopped borrowing the footer’s padding and border: they read --cui-date-picker-ranges-* and --cui-date-picker-timepickers-*.

Link decoration is a token, not a Sass knob

  • Breaking $link-decoration, $link-underline-offset and $link-hover-decoration are gone. The underline lives on :root as --cui-link-decoration (underline) and --cui-link-underline-offset (.2em); set the token instead of recompiling. --cui-link-hover-decoration is no longer declared — the hover falls back to --cui-link-decoration, so declare it yourself for a different hover. Nav links, list-group actions, page links, the header, the dropdown item and the button write text-decoration: none outright (they used to skip it when the knob was already none), and .btn-link reads the tokens.

Every theme colour gets an action-background slot

:root emits --cui-{color}-bg for every theme colour, pointing at the colour’s base token. Active and checked states read the slot instead of the base directly — --cui-list-group-active-bg, --cui-menu-item-active-bg, --cui-pagination-active-bg, --cui-nav-pills-link-active-bg, --cui-progress-bar-bg and --cui-range-thumb-bg are all var(--cui-primary-bg) now. The resolved values are unchanged; the slot is a single place to retune what “filled with the theme colour” means without touching the base colour that text and borders derive from. (The secondary colour’s slot takes over the name of the former surface alias — see the ladder entry above.)

  • A .theme-* class reads the colour’s -bg slot, not its base. --cui-theme-bg is var(--cui-danger-bg) now (was var(--cui-danger)), so overriding --cui-danger-bg retunes every checked, active and filled state under the class, as the colour slots page describes. The trade-off: --cui-danger-bg resolves on :root, so a --cui-danger override on a single element no longer reaches the theme class on it — override the colour on :root, or set --cui-danger-bg on the element.

Colour decisions are written, not computed

v6 stops evaluating colours at build time, the way upstream v6 does — Sass assembles maps of CSS expressions and the browser resolves them.

  • The contrast slot holds written values instead of color-contrast() results. The computed and written values are identical, so nothing renders differently; the point is that a theme colour no longer has to be a Sass colour for the contrast pass to run over it. Upstream keeps a "contrast" key per colour and never calls the function either.
  • Table variants read the theme tokens. Breaking .table-primary and friends still exist, but they are generated the way .btn-primary is: the class sets --cui-theme-* and the base .table rules read it. $table-variants is now a list of colour names, not a map of pre-shifted colours, and $table-bg-scale / $table-border-factor are gone. A theme colour you add yourself now gets a table variant without compiling Sass. Two visible consequences: the variant background is the colour’s bg-subtle token rather than a shift-color() of the base, and striped / hover / active are color-mix() overlays on the text colour rather than opaque mixes — so they compose over the row’s own background. Table variants also follow colour modes now, where before they stayed on light-palette values in dark mode.

The theme colours are retuned so white text reads on them

Breaking Four of the five base colours moved, and success, info and danger now carry white contrast text instead of black. The bases were picked at the brightest point where white text still clears both contrast gates: WCAG 4.5:1 and APCA Lc 75, the APCA threshold for body text. Before this, only primary paired with white, because the bases sat at lightnesses between 61 and 81 that no dark-on-light pairing and no light-on-dark pairing could both satisfy.

RGB channel tokens and the elevation system removed

Breaking

  • Every --cui-{name}-rgb custom property is gone, along with the $theme-colors-rgb and $theme-colors-rgb-dark maps, the to-rgb() function’s role in :root, and the rgba-css-var() and translucent-css-var() helpers (color-var-ref() is the function that stays — see the utilities section). They existed only so rgba(var(--cui-primary-rgb), .5) could apply an alpha to a token; that is what color-mix() does directly:

    - background-color: rgba(var(--cui-primary-rgb), .5);
+ background-color: color-mix(in srgb, var(--cui-primary) 50%, transparent);

    Upstream v6 carries no rgb triplets either. The opacity utilities (.text-opacity-50, .bg-opacity-25, .link-opacity-75) are unchanged — they now scale the token through calc(var(--cui-bg-opacity) * 100%).

  • The elevation system is gone: $elevations, $enable-elevations, $elevation-base-color, the elevation() mixin and the .elevation-* utilities. It was disabled by default ($enable-elevations: false), so the utilities were the only reachable part. Use the shadow utilities (.shadow, .shadow-sm, .shadow-lg) or set box-shadow directly.

  • The button focus ring is the theme ring. --cui-btn-focus-shadow-rgb and the per-variant $btn-*-focus-shadow-rgb Sass variables are gone without a renamed successor, and so is --cui-btn-focus-ring: the button draws the ring from the global width and the theme’s colour, so a colour button rings in its colour and a neutral one gets the global ring. To restyle it, set --cui-focus-ring-color (or --cui-theme-focus-ring) on the button. Two visible consequences: a colour button’s ring uses the focus-ring opacity (fainter than the old 50% mix), and the neutral outline/ghost buttons ring in the global colour instead of a grey.

Focus rings are keyboard-only on activation controls

Breaking

Controls you click to act — checkboxes, radios, switches, both range sliders, pagination links, stepper buttons, the search, close, sidebar and navbar togglers — draw their focus ring on :focus-visible, so clicking no longer flashes it and keyboard focus still shows it, joining the buttons which already worked this way. Fields you type into — text inputs, the OTP cells, the date-time sections — keep :focus: a field shows its ring on mouse focus by design.

Two suppressed rings are restored: the header toggler and the carousel controls declared outline: 0 with no replacement, so keyboard focus was invisible on both.

$component-active-color and $component-active-bg are removed

Breaking

One shared pair in _config.scss fed every active state in the library — the list group, pagination, the menu, nav pills, the dropdown, both range sliders and the checkable controls. A theme colour is one nested map entry

Breaking

$theme-colors carried one value per colour and three further families carried the rest, so a theme colour was defined in four places and adding one meant editing four blocks. It is a map of maps now — one name, eight slots.

  • Twenty-four Sass variables are removed: $primary-text-emphasis and its seven siblings, $primary-bg-subtle and its seven, $primary-border-subtle and its seven. Override a slot through the map instead:

    Every --cui-{color}-* custom property keeps its name and its value, so a runtime override is unaffected.

The OTP input defaults to the shared frame

Breaking

The neutral surfaces are a numbered ladder

.bg-body-secondary, .bg-body-tertiary, .text-body-secondary and .text-body-tertiary are deprecated. The replacements are ordinal: .bg-1 … .bg-4 for surfaces and .fg-body, .fg-1 … .fg-4 for the text hierarchy, with two new rungs (.bg-1, .bg-2 on new gray-025 / gray-050 stops) between the body and the old surfaces. The deprecated names render identically and are removed in v7.

The adjectives ran backwards for backgrounds — “tertiary” sat closer to the page than “secondary” — because for text, where the names came from, “stronger” means more visible, while for a surface it means further from the page. Numbers say how far from the body a rung sits and read the same on both sides.

The deprecated surface names follow the two-rung step of the rest of the library: .bg-body-secondary renders --cui-bg-3 and .bg-body-tertiary --cui-bg-2 (gray-100 / gray-050 in the light scheme, the v5 stops one rung apart), .text-body-secondary stays --cui-fg-2 and .text-body-tertiary --cui-fg-3 — tertiary text was the lighter of the two in v5 and still is.

Two consequences for the tokens:

  • Deprecated The surface tokens move out of the theme-color namespace. --cui-bg-body, --cui-bg-1 … --cui-bg-4 and --cui-fg-body, --cui-fg-1 … --cui-fg-4 are canonical; --cui-body-bg, --cui-body-color, --cui-secondary-color (--cui-fg-2), --cui-tertiary-color (--cui-fg-3) and --cui-tertiary-bg (--cui-bg-2) remain as aliases with identical values, and go away in v7 — at which point the --cui-secondary-* prefix belongs to the secondary theme color alone. One alias is already gone: Breaking --cui-secondary-bg is the secondary theme color’s action-background slot now (see the entry below), not a surface alias. Markup that read it for the surface gets a similar but lighter gray — read --cui-bg-4 instead. This name is exactly why the ladder moved out of the theme-color namespace: a page surface sat next to --cui-secondary-bg-subtle (a theme-color slot) with no way to tell which system a token belonged to.
  • Breaking The dark side of the ladder is palette stops, and the page got darker. The grays gain --cui-gray-950 (#15181f) and --cui-gray-975 (#0e1115), and every dark rung is a stop instead of a color-mix() between gray-800 and gray-900: the body sits on gray-975 (was gray-900), bg-1 on gray-950, bg-2 on gray-900, bg-3 on gray-800 and bg-4 on gray-700. Dark mode reads darker overall and surfaces have more room to step away from the page. --cui-border-color-translucent is one expression for both schemes, color-mix(in oklch, var(--cui-fg-body) 15%, transparent), instead of two rgba() values computed in Sass; the color-translucent() function is gone. Override the $bg-* knobs or the --cui-bg-* tokens to keep the previous palette.
  • Breaking The text ladder is solid grays, and components use all of its rungs. --cui-fg-body through --cui-fg-4 were alpha blends of one color (rgba(…, .95) down to .25), which made the two deepest rungs illegible and left every component crowded onto fg-body/fg-2. Each rung is a palette stop now — fg-body on gray-900/050, fg-1 on 800/200, fg-2 on 700/300, fg-3 on 600/500, fg-4 on 500/600 — so contrast is the same on any surface and can be audited once. Components spread across the rungs: secondary text (breadcrumb links, toast headers, captions, blockquote footers) reads fg-3 instead of fg-2, disabled states read fg-3/fg-4 and stay legible, dividers read fg-4, and the strongest text (tables, active nav links, the tooltip surface) reads fg-body instead of --cui-emphasis-color. Nav links are neutral (fg-2, darkening through fg-1 to fg-body when active) instead of link-colored — a .theme-* class still recolors them. $gray-base fed the alpha blends and is removed. Override the $fg-* knobs or the --cui-fg-* tokens to keep the previous rendering.
  • .text-body and .text-body-emphasis are unaffected — they are not ordinal, any more than .text-primary is.
  • Breaking The Sass knobs follow the ladder. The $theme-fgs and $theme-bgs maps ("body", "1" … "4") replace $body-color, $body-bg, $body-secondary-color, $body-secondary-bg, $body-tertiary-color and $body-tertiary-bg; every entry holds one light-dark() expression, so $body-bg-dark and $body-tertiary-bg-dark are gone too — the translucent tints that needed their Sass colors read the grays inline.

light and dark are replaced by inverse

Breaking

light and dark were theme colours whose names described a colour scheme, and they behaved like it: .theme-dark sat next to data-coreui-theme="dark" meaning something else entirely, and neither followed the reader’s scheme — a .btn-dark stayed near-black on a near-black page. There are seven theme colours now, and the two neutrals swap ends of the gray scale between schemes.

  • inverse replaces dark. It resolves to gray-900 in light mode and gray-100 in dark, so .btn-inverse, .text-bg-inverse and .table-inverse stand against the page in both.
  • secondary takes over what light did. It is a light neutral now (gray-100 in light mode, gray-600 in dark) rather than the mid gray-blue #6b7785, so .btn-secondary and .bg-secondary change appearance.
  • Every -light and -dark class is gone. Rename -dark to -inverse and -light to -secondary across alert, bg, border (and its per-side variants), btn, btn-ghost, btn-outline, btn-subtle, callout, chip, focus-ring, underline, list-group-item, shadow, table, text, text-bg and theme, plus the -subtle and -emphasis families. The colour-scheme opt-ins keep their names: .navbar-dark, .dropdown-menu-dark, .carousel-dark and .sidebar-dark are unaffected, as is .fw-light.
  • A surface is not a theme colour. Where .bg-light was a neutral panel, reach for .bg-4 or .bg-3; where .bg-dark was a fixed dark backdrop, set data-coreui-theme="dark" on the container and let the surface classes follow.
  • --cui-theme-base is now --cui-theme-bg. The contextual token that components read for a fill was named after the map slot rather than the job; the slot is still base, and --cui-{color} is unchanged.
  • Colour utilities read the slot that stays legible. .text-* points at --cui-{color}-fg instead of the raw colour, and .btn-outline-* and .btn-ghost-* take their text from it too. For the five chromatic colours this is a shade darker in light mode and a shade lighter in dark; for the neutrals it is the difference between readable and gray-on-gray. .btn-outline-* also takes its border from the border slot, so the outline is a subtle line rather than a full-strength one. .bg-* and .border-* keep reading the colour itself.
  • $light and $dark are removed; inverse is new. Neither secondary nor inverse is a hue of its own: they read --cui-gray-200 and --cui-gray-900, and there is no Sass colour behind them to pass to color-contrast() or the tint/shade functions — read $gray-* for that.
  • $utilities-colors is removed. It was a flat name → colour copy of the map’s base slot, and no utility reads the raw colour for every family any more. Call map-get-nested($theme-colors, "base") where you need one, or theme-color-refs("fg") for the slot a text utility uses.
  • $theme-lightness-overrides is now $theme-state-colors and carries ready values rather than lightness multipliers. A single multiplier cannot serve a colour that is dark in one scheme and light in the other, so the two neutrals step along the gray scale instead.

Component icons render through CSS masks

Breaking

The accordion chevron and the carousel arrows were background-image SVGs with the colour written inside the markup, which is why each needed a dark-mode rule — the accordion swapped in a second SVG, the carousel inverted the first with a filter. They are now painted through a CSS mask, so the colour lives on background-color as an ordinary token and follows the root colours by itself. Upstream v6 does the same, with a mask-icon() mixin.

  • The accordion’s icon is one shape recoloured per state, not two images. --cui-accordion-header-active-icon no longer has to carry a second copy of the artwork: it defaults to --cui-accordion-header-icon, and the open state changes --cui-accordion-header-active-icon-color instead. Set it only when the open state is a genuinely different shape — a minus against a plus. New tokens: --cui-accordion-header-icon-color and --cui-accordion-header-active-icon-color.
  • A custom icon is now a shape, not a coloured image. Whatever colour you put inside $accordion-header-icon or $carousel-control-prev-icon-bg / $carousel-control-next-icon-bg is ignored — only the alpha of the SVG is used. Set the colour through the token (--cui-accordion-header-icon-color, --cui-carousel-control-color).
  • $accordion-icon-color and $accordion-icon-active-color are currentcolor now, not Sass colours — Sass colour functions on them no longer work. The icon therefore takes the header’s colour in every state, so anything that recolours an open header (--cui-accordion-active-color, a .theme-{color} class) carries the icon with it. Both tokens stay, for the case where the icon is meant to differ from the text.
  • $carousel-control-icon-filter is removed, with its --cui-carousel-control-icon-filter custom property and its two dark companions ($carousel-control-icon-filter-dark, $carousel-dark-control-icon-filter), along with the four accordion dark variables ($accordion-icon-color-dark, $accordion-icon-active-color-dark, $accordion-button-icon-dark, $accordion-button-active-icon-dark). The accordion’s dark-mode block is gone entirely.
  • The carousel’s colours are tokens. --cui-carousel-control-color is new; .carousel-dark pins the dark side of each pair through $carousel-dark-control-color, $carousel-dark-indicator-active-bg and $carousel-dark-caption-color (previously $carousel-*-dark in _variables-dark.scss). RTL still swaps the two arrows, now through mask-image.
  • Visible in dark mode: the old dark accordion chevron was a filled glyph where the light one was stroked. Both modes now use the stroked shape — same colour, same size, slightly different drawing. Worth knowing if you diff screenshots.

Buttons

  • Breaking button-variant() takes a variant name, not a colour pair, and reads it from $button-variants. Each entry of that map names, per state, the theme token a button variable reads and the neutral value behind it; disabled repeats base. button-outline-variant() and button-ghost-variant() are removed (they are entries in the map now), and scss/mixins/_buttons.scss no longer exists — the mixin lives next to the map in scss/buttons/_button.scss.

  • Hover and active shades are computed in CSS with oklch(from var(--cui-primary) calc(l * …) c h) instead of precompiled shade-color()/tint-color(). Shades shift slightly (measured 8–23 per RGB channel). The win: a theme color you add yourself gets correct hover/active states without compiling Sass.

  • The eight shade/tint amount knobs are removed: $btn-hover-bg-shade-amount, $btn-hover-bg-tint-amount, $btn-hover-border-shade-amount, $btn-hover-border-tint-amount and the four $btn-active-* counterparts. They fed the Sass mixes that no longer happen.

  • Breaking The interaction shade belongs to the theme, not to the button. Every .theme-* class emits --cui-theme-hover and --cui-theme-active — its own colour, shifted in lightness — and the button variants read them, so a component that wants “this theme colour, one step darker” no longer has to recompute it. The knobs moved with them: $btn-hover-lightness, $btn-active-lightness and $btn-lightness-overrides are now $theme-hover-lightness, $theme-active-lightness and $theme-state-colors in scss/_theme.scss.

  • The interaction shade is a runtime knob, and it keeps its saturation. The multipliers are :root tokens — --cui-theme-hover-lightness, --cui-theme-hover-chroma, --cui-theme-active-lightness, --cui-theme-active-chroma — so the strength of every hover and active state is one override, on the page or on a subtree, where it used to be a Sass value baked into each theme class. The shade also multiplies chroma (1.1 on hover, 1.15 on active) where it used to keep it, so a pressed button no longer fades as it darkens; the lightness steps are unchanged.

  • The dark-mode button block is gone (~160 lines of CSS) — variants follow the root color tokens, which already switch in dark mode.

  • Breaking The $btn-* variables that only forwarded a shared value are removed: $btn-color, $btn-padding-y, $btn-padding-x, $btn-font-family, $btn-font-size, $btn-line-height, $btn-border-width, $btn-border-radius, $btn-disabled-opacity, $btn-transition-* and the -sm/-lg pairs. They pointed at --cui-btn-input-*, so a value assigned to them was overwritten by the token anyway. Configure the frame once on :root with the $input-btn-* variables, or set --cui-btn-* on the button.

  • Breaking $btn-font-weight is removed, and buttons take their weight from the shared frame. --cui-btn-font-weight reads --cui-btn-input-font-weight, the weight fields and input group addons use, which defaults to --cui-body-font-weight on :root. A page that sets a lighter body weight gets lighter buttons with it; .btn-link keeps the normal weight. Set --cui-btn-font-weight on .btn to change buttons alone, or --cui-btn-input-font-weight on :root to change buttons and fields together.

  • Breaking button-size() is removed. Sizes are a loop over $button-sizes, which points the button’s tokens at the matching --cui-btn-input-{size}-* set. Add a size by adding its tokens on :root and its name to the map.

  • New tokens on .btn: --cui-btn-gap, --cui-btn-min-height, --cui-btn-white-space and --cui-btn-transition-property / -duration / -timing. The transition was read straight from the shared --cui-btn-input-* tokens before, so it could not be retuned per button.

  • Breaking .btn-close draws its focus ring as an outline, like every other control; $btn-close-focus-shadow and --cui-btn-close-focus-shadow are removed. A box-shadow ring was clipped by the overflow: hidden of the modal, toast or drawer the close button usually sits in. Its geometry is tokens now too: --cui-btn-close-width, -height, -padding-x, -padding-y.

  • .btn-primary, .btn-outline-*, .btn-ghost-* class APIs are unchanged.

  • Toggle buttons: .btn-check moves onto the <label>, with the input nested inside. A toggle button was two elements held together by an id/for pair; it is one element now, so nothing can fall out of sync:

    - <input type="checkbox" class="btn-check" id="t" autocomplete="off">
- <label class="btn btn-primary" for="t">Toggle</label>
+ <label class="btn btn-primary btn-check">
+   <input type="checkbox" autocomplete="off">
+   Toggle
+ </label>

    The states read the nested input with :has() instead of sibling selectors, and a .btn-group stops having to reason about a hidden child that is not a button. The old spelling keeps working — the label carries .btn in the new one, so the two select themselves apart — and renders identically; it is deprecated in v6 and removed in v7. One behavior is deliberately carried over: a disabled toggle is dimmed rather than repainted, so a disabled checked toggle still reads as checked.

Utilities API: one property map replaces css-var, css-variable-name and local-vars

Breaking

Three keys said one thing between them — a utility may write custom properties, real properties, or both — and property now says it alone. Give it a map: a null entry receives the utility’s value, everything else is written as declared.

  "background-color": (
-   property: background-color,
-   local-vars: ("bg-opacity": 1),
+   property: (
+     --#{$prefix}bg: null,
+     --#{$prefix}bg-opacity: 1,
+     background-color: color-mix(in srgb, var(--#{$prefix}bg) calc(var(--#{$prefix}bg-opacity) * 100%), transparent),
+   ),
    class: bg,
    values: $utilities-bg-colors
  )

  "bg-opacity": (
-   css-var: true,
+   property: (--#{$prefix}bg-opacity: null),
    class: bg-opacity,
    values: (25: .25, 50: .5, 75: .75)
  )

The class API does not change — .bg-primary and .bg-opacity-50 still exist and still compose. What changes is where the translucency expression lives:

  • $utilities-text-colors, $utilities-bg-colors, $utilities-border-colors and $utilities-links-underline now carry plain token references (var(--cui-primary), var(--cui-primary-fg)) instead of a color-mix() expression per entry. The expression is written once, in the utility’s property map. If you built a map of your own by calling translucent-css-var(), call color-var-ref() instead — same arguments, without the wrapper; translucent-css-var() is removed, along with the unused map-loop() and color-contrast-variables().
  • .text-body-secondary now responds to .text-opacity-*. It rendered the same colour before and renders the same colour now; it simply went through the plain value and so ignored the opacity knob every other colour utility honoured.
  • Every custom property a utility assigns is registered @property { inherits: false }, which now covers --cui-bg, --cui-text, --cui-border and --cui-underline as well — so a colour set on a container cannot leak into a descendant that only carries an opacity class.

at-property: false still opts a utility out of that registration, for the one case that writes an inheriting global token (.focus-ring-*).

Utilities API: child selectors and attribute selectors (new)

Two keys join the $utilities API, ported from Bootstrap’s v6 branch:

  • child-selector makes a utility style the children of the element it is applied to instead of the element itself, wrapped in :where() so it adds no specificity. This is what the new spacing and divider utilities are built on.
  • selector (class, attr-starts, attr-includes) writes an attribute selector rather than a class, so one rule can serve a whole family of classes.

They bring four new utilities with them, all responsive and direction-aware:

classwhat it does
.space-x-*, .space-y-*margin between children — gap without needing a flex or grid container
.divide-x, .divide-y (+ -0)a border between children, none on the outer edges

Nothing existing changes; these are additions. See the utilities API, spacing and borders.

Utilities API: theme variants and the rtl key removed

Breaking
  • The dark: theme-variant utilities are gone (40 classes: .dark\:bg-*, .dark\:text-*). They were generated for the colour utilities only, duplicating every value under a [data-coreui-theme=dark] selector, and were never documented. The palette already resolves per theme through light-dark(), so .bg-body, .text-body-secondary and friends follow the colour mode on their own. The dark-mode key of a $utilities entry is no longer read.
  • The rtl key of a $utilities entry is no longer read. It did two jobs: rtl: false wrapped the output in RTLCSS /* rtl:remove */ directives, and rtl: true accepted ("ltr": …, "rtl": …) value maps that emitted a [dir="rtl"] counterpart. Direction is expressed with logical properties now (the position utilities are inset-inline-start/-end), so the flag has nothing left to do. One behaviour change comes with it: the RTL behaviour of .translate-middle / .translate-middle-x is written as a plain :dir(rtl) rule instead of a generator option — transform is not direction-aware, so centring on a logical inset still needs the flip, but it is the only utility that does and it no longer costs the whole API a key.

RFS removed

Breaking
  • The RFS engine is gone — no vendor/rfs, no font-size() / rfs() mixins, no $enable-rfs, no rfs option in the utilities API, and none of the $rfs-* knobs ($rfs-base-value, $rfs-breakpoint, $rfs-factor, $rfs-mode, $rfs-unit, $rfs-two-dimensional, $rfs-class, …). Fluid type is written as literal clamp() values in the $font-sizes map, $display-font-sizes and $legend-font-size; rendering is unchanged at every viewport width.
  • Headings no longer derive from $font-size-base — a clamp() cannot be multiplied. Override the stop in $font-sizes directly.
  • A temporary scss/vendor/_rfs.scss shim (pass-through font-size()/rfs() mixins) exists only for the docs engine and will be removed — do not depend on it.

One styling surface for all text controls

  • Shared root knobs: :root now carries the control frame (--cui-btn-input-padding-y/-x, -font-family/-size, -line-height, -border-width, -transition, -color, -bg, -disabled-opacity, plus -sm-*/-lg-* size sets) and the selection state (--cui-control-checked-bg/-border-color, --cui-control-indeterminate-bg/-border-color). Restyle these once and every control follows: inputs, selects, checks, switches, OTP, chip input, autocomplete, multi select, and the pickers — including the checkbox-style option indicators inside autocomplete and multi select.
  • Every text control consumes per-element --cui-control-* tokens (padding, font, colors, border, radius, shadows, focus and disabled sets) that default to those knobs. Override a single control on its element; override everything at :root. Breaking The component-namespace custom properties that duplicated this frame are renamed: --cui-autocomplete-padding-y, --cui-date-picker-font-size, --cui-time-picker-bg, --cui-form-multi-select-border-color, --cui-chip-input-padding-x and the rest of their frame sets are now --cui-control-* on the same elements. Runtime overrides written against the old names must be updated. Component-specific tokens (indicators, dropdowns, cells, cleaner buttons) keep their names. Three v5 names that survived as undeclared fallbacks are gone too: --cui-input-placeholder-color (set --cui-control-placeholder-color), --cui-input-focus-border-color in the combobox (set --cui-btn-input-focus-border-color) and --cui-table-caption-color (the caption reads $caption-color).
  • Component Sass variables survive with new defaults: $date-picker-bg, $autocomplete-padding-y and the rest now default to the shared knob (var(--cui-btn-input-bg) …). Untouched, the control follows the shared surface; overridden through with(), it detaches just that control — exactly what reaching for a component knob means.
  • The select’s indicator geometry is computed at runtime. $form-select-indicator-padding and $form-select-feedback-icon-padding-end are now calc() expressions over var(--cui-control-padding-x) instead of Sass products, and $form-select-bg-position carries the var() inside it (the mirrored keyword comes from the :dir(rtl) rule in the same sheet). Breaking Sass arithmetic on these variables in your own stylesheets no longer works — they are CSS calc strings now, not numbers. Override them with your own calc() or a plain length instead.
  • Form tooltips reuse the tooltip’s runtime tokens. Add the .tooltip class to a feedback tooltip (class="tooltip invalid-tooltip") and it follows tooltip theming — --cui-tooltip-padding-*, -font-size, -border-radius — the upstream v6 contract. Bare .invalid-tooltip markup keeps rendering exactly as before through built-in fallbacks. Breaking The Sass-level derivation is gone: $form-feedback-tooltip-* no longer default to $tooltip-*, so overriding $tooltip-padding-y alone no longer moves feedback tooltips at compile time — use the runtime link (add the class) or set $form-feedback-tooltip-* explicitly. The tooltip variables moved to scss/_tooltip.scss, the feedback set to scss/mixins/_form-validation.scss.
  • Validation composes through the tokens: .is-invalid / .is-valid set --cui-control-border-color, -focus-border-color and -focus-ring instead of restating declarations, so state styling follows any control automatically.

The spacing scale is computed from --cui-spacer in the browser

  • Breaking --cui-spacer-1 … -12 are calc() multiples of --cui-spacer, and the spacing utilities read the stops. $spacers used to multiply $spacer when the stylesheet was built and every .m-*, .p-*, .gap-*, .space-* and .g-* class carried the literal length, so the only way to rescale spacing was to recompile. Now :root declares --cui-spacer ($spacer, 1rem) and the stops as calc(var(--cui-spacer) * n), the utilities write var(--cui-spacer-n), the negative margins and the .w-* sizes calc(var(--cui-spacer) * n), and the gutters read the same stops. :root { --cui-spacer: .75rem } rescales all of it at run time, and overriding one stop re-spaces every utility on it. The scale moved next to the breakpoints in scss/layout/_tokens.scss, so the grid, utilities and reboot bundles each declare it; a $root-tokens override of a --cui-spacer-* key no longer reaches it — override the custom property instead.

The border-width scale is computed from --cui-border-width in the browser

  • Breaking --cui-border-width-1 … -5 and -keyline are calc() multiples of --cui-border-width, and the .border-* width classes read them. $border-widths shipped literal pixel values and every .border-2, .border-top-3, .border-start-5 class carried the length, so changing --cui-border-width re-weighted the components and left the utilities where they were. Now :root declares the stops as multiples of --cui-border-width (1px): -keyline is half of it, -1 the base, -2 … -5 its multiples, and the width classes write var(--cui-border-width-n). :root { --cui-border-width: 2px } re-weights utilities and components together; overriding one stop re-weights every class on it. --cui-border-width-keyline keeps its name and moves into the scale.

Spacing utilities write logical shorthands

.mx-*, .my-*, .px-* and .py-* (and their negative-margin variants) emit margin-inline, margin-block, padding-inline and padding-block instead of two physical longhands each. Rendering is identical in both directions; the only visible difference is in DevTools, where one shorthand replaces the pair, and in a stylesheet of your own that overrode one of the longhands after ours — a shorthand still yields to a later longhand.

Opacity utilities no longer cascade to descendants

Breaking

The opacity utilities compose through custom properties — .text-opacity-50 sets --cui-text-opacity and the colour utilities read it. Custom properties inherit, so the value leaked into every descendant. The colour utilities that restate their own opacity (.text-primary declares --cui-text-opacity: 1) were immune; the ones reading it through a var(…, 1) fallback were not.

Reachable consequences in v5: .bg-opacity-25 on a container faded every nested .text-bg-*, and .link-opacity-50 faded every nested link — including bare <a> elements, which read --cui-link-opacity too.

Five names are now registered with @property as inherits: false, so each utility is scoped to the element it is applied to: --cui-text-opacity, --cui-bg-opacity, --cui-border-opacity, --cui-link-opacity, --cui-underline-opacity. Upstream v6 does the same.

  • If you relied on the leak — one .link-opacity-* on a wrapper fading a whole block of links — put the utility on each element, or set the custom property yourself in your own CSS (a hand-written declaration still inherits; only the registration changes how utilities behave).
  • .focus-ring-* is deliberately not registered: it writes --cui-focus-ring-color, which is a global :root token, and components read it without a fallback. A custom utility that writes a :root token name must opt out the same way, with at-property: false in its $utilities entry.
  • Compiled output is otherwise byte-identical — the five @property blocks are the whole diff.

The CSS Grid ships, and its responsive classes are container queries

Breaking

$enable-cssgrid is true by default, so .grid and the .g-col-* / .g-start-* classes are in the compiled CSS instead of waiting behind a Sass flag. Set it to false if you do not want them.

Every .grid is now a query container (container-type: inline-size), so .g-col-md-6 responds to the width of the grid rather than to the viewport — a grid inside a narrow column switches layout on that column’s width. This is what upstream v6 does, and it is the point of having a second grid at all.

container-type implies layout containment, so a .grid is the containing block for absolutely and fixed-positioned descendants: position: fixed inside a grid is positioned against the grid, not the viewport. Our own floating panels render through a portal and are unaffected; your own fixed markup has to live outside.

The CSS Grid declares its variables, and nested grids no longer inherit

Breaking

.grid read --cui-rows, --cui-columns and --cui-gap through a var() fallback and declared none of them. Two consequences: the variables did not appear in dev tools, and — because a custom property that is never declared simply inherits — a nested .grid picked up the column count of the grid around it.

All three are declared on .grid now, so every grid starts from twelve columns, one row and the standard gap regardless of its surroundings. A component built on .grid keeps its own layout wherever it is dropped.

If you relied on a nested grid inheriting, set the variable on that grid too:

<div class="grid" style="--cui-columns: 3;">
  <div>
    <div class="grid" style="--cui-columns: 3;">...</div>
  </div>

The cq-* grid is gone

Breaking

v5.3.0 shipped a second, experimental grid — .cq-container, .cq-row, .cq-col-*, .cq-offset-*, .cq-g-* — behind $enable-container-queries, with its own $cq-grid-breakpoints map that duplicated $grid-breakpoints value for value. It never shipped in the default build, and maintaining two grids to express one idea is what the CSS Grid above now does properly.

The flag, the map, the classes and the make-c-grid-columns() mixin are all removed. If you configured $enable-container-queries, drop it: @use ... with () errors on a variable the module no longer declares. If you had opted in: .cq-row/.cq-col-* map onto the CSS Grid (.grid + .g-col-*), which is container-based by default, or onto the flexbox grid (.row/.col-*) if you want viewport breakpoints. To keep the container behaviour on markup of your own, mark the element with .contains-inline and write the query with the container-breakpoint-* mixins.

Breakpoint mixins emit range queries

Breaking

media-breakpoint-* now emits (width >= 768px) / (width < 768px) instead of (min-width: 768px) / (max-width: 767.98px). The .02px subtraction existed to work around min-/max- prefixes on fractional viewports; range syntax makes it unnecessary.

breakpoint-max() returns the raw breakpoint value now (768px, not 767.98px). If you call it yourself inside a max-width: query, subtract the .02px there or move that query to range syntax too — otherwise the two breakpoints overlap on exactly 768px.

The container-breakpoint-* mixins use the same syntax, take an optional container name as their second argument, and default to $grid-breakpoints:

@include container-breakpoint-up(md) { … }              // nearest container
@include container-breakpoint-up(md, sidebar) { … }      // @container sidebar (width >= 768px)

set-container($type, $name) is new and marks an element as a query container.

New: container-type utilities

.contains-inline and .contains-size set container-type, so you can make any element a query container from markup. See Container queries.

@import is no longer supported

Breaking

The 87 *.import.scss files that let @import reach our modules are gone, so an @import of anything under scss/ no longer resolves. Load the library with @use instead:

// Was
@import "../node_modules/@coreui/coreui/scss/coreui";

// Is
@use "@coreui/coreui/scss/coreui";

Configuration moves with it. Where @import let you set variables by declaring them before the import, @use takes them in a with () clause, and the rule has to be the first thing in the file:

@use "@coreui/coreui/scss/coreui" with (
  $body-bg: #000,
  $body-color: #111
);

Sass deprecated @import and removes it in Dart Sass 3.0.0, so this is where it was heading regardless. The Sass migration guide covers the rules; sass-migrator module automates most of a conversion.

One consequence worth calling out: a module is configured once, at load time. If your change has to read a default before changing it — merging into $utilities, for instance — it goes in a partial you load before the library. The utilities API page shows both patterns.

What we deliberately did not copy. Upstream renamed three components and their classes — .modal, .offcanvas, .dropdown, .dropdown-menu and .dropdown-item are gone from Bootstrap v6, replaced by .dialog, .drawer, .menu and .menu-item. Those are three of the most-used components in any Bootstrap app, so _modal.scss, _offcanvas.scss and _dropdown.scss keep their names and their classes here.

The colour system has its own modules

Breaking

The type scale is one named map

One scale now carries every font size the library renders, each stop with the line height that belongs to it — upstream’s mechanic, with our values, so nothing moves on screen:

$font-sizes: (
  "xs":  ("font-size": .75rem,        "line-height": 1.5),
  ...
  "4xl": ("font-size": clamp(1.375rem, 1.375rem + 1.5vw, 2.5rem), "line-height": 1.2)
);

  • $font-sizes changed shape — it was (1: $h1-font-size, … 6: $h6-font-size) and is now keyed xs, sm, md, lg, xl, 2xl, 3xl, 4xl, 5xl, 6xl, with a nested map per stop. The two top stops sit above the headings — display sizes ($font-size-5xl/-6xl, up to 3rem and 3.5rem) continuing the same fluid progression, numerically level with the former .display-5 and .display-4. Breaking If you overrode $font-sizes, move your values into the new shape. The numeric keys live on in $font-sizes-legacy, which is derived from the named scale.

  • :root gets --cui-font-size-* and --cui-line-height-* per stop, and h1–h6 read the tokens instead of the Sass variables. Restyling a stop at runtime now moves every heading and utility that uses it. $h1-font-size … $h6-font-size, $font-size-sm/-lg, $font-size-5xl/-6xl and $zindex-* are gone: each was read only by the map it fed, so the maps ($font-sizes, $zindex-levels) hold the values and are the override point, in the defaults() shape — set one key and the rest stays. $font-weight-* remain and feed $font-weights the same way.

  • New: .fs-{stop} alongside .fs-1 … .fs-6, which keep working and render identically — .fs-1 is .fs-4xl, down to .fs-6, which is .fs-md.

  • New: .text-{stop}, which sets font-size and line-height together.

  • Breaking .display-1 … .display-6 and .lead are removed, with $display-font-sizes, $display-font-family, $display-font-style, $display-font-weight, $display-line-height, $lead-font-size and $lead-font-weight. They were a fixed size and weight next to a scale that already carries those sizes: .display-4 is .fs-6xl, .display-5 is .fs-5xl, and .lead is .fs-lg; add .fw-light for the weight the old classes carried and .lh-1 for the display line height. The three larger display sizes have no stop of their own — set font-size yourself or extend $font-sizes.

We did not follow upstream’s other typography changes. Bootstrap v6 also deletes .fs-1 … .fs-6 and retunes the sizes — h1–h3 grow up to 10px on small screens while h4–h6 shrink at every width. Those classes stay, at their current sizes.

The focus ring is an outline

Breaking

Focus rings were drawn with box-shadow and are now drawn with outline, following upstream v6. The practical win is that an outline is not clipped by an ancestor’s overflow — the ring stays visible inside scroll containers, where a box-shadow ring was cut off.

  • The per-component ring custom properties are gone, not renamed. Every --cui-*-focus-box-shadow — button, pagination, accordion button, check, radio, switch, calendar cell and nav button, stepper indicator, range-slider thumb, search button, combobox, chip — had exactly one value, and the ring is now drawn from the global width and the theme’s colour wherever it appears. Restyle it with --cui-focus-ring-color / --cui-focus-ring-width for the whole page, or set either on the component itself for one instance.

    - --cui-btn-focus-box-shadow: 0 0 0 .25rem rgba(88, 86, 214, .5);
+ --cui-focus-ring-color: rgba(88, 86, 214, .5);

    A runtime override written against an old name is now inert — there is no fallback path, because the value goes to a different property.

    Form fields draw the same ring: the text input, select, control group, date-time field, OTP cell and List Box option read the theme’s focus ring or --cui-focus-ring-color, and a validation state draws its own ring in its colour. The ring has no per-field colour token.

  • The Sass variables follow: $focus-ring-box-shadow → $focus-ring, and the per-component ones ($btn-focus-box-shadow, $pagination-focus-ring, $combobox-focus-ring, $form-check-input-focus-ring, …) are removed.

  • $focus-ring-blur is gone, along with --cui-focus-ring-x, -y and -blur. An outline has no blur or offset vector. New: $focus-ring-offset / --cui-focus-ring-offset (defaults to 0), which pushes the ring away from the element, and --cui-focus-ring, the composite shorthand the mixin reads.

  • focus-ring() changed signature to focus-ring($offset: false, $color: null). It no longer emits outline: 0. Every ring in the library is drawn through it; with no arguments it draws the themed ring, and $color swaps the hue for one rule — which is how the validation states ring in red and green.

  • --cui-focus-ring-offset actually applies. The mixin emits outline-offset wherever a ring is drawn, so one declaration moves every ring in or out. It was previously read by the .focus-ring helper alone, which made the token look supported while doing nothing on any component.

  • $pagination-focus-outline is gone — the outline is now the ring itself.

  • A component ring is a reference to the global one, not a copy of it. Every ring resolves as var(--cui-focus-ring-width) solid var(--cui-theme-focus-ring, var(--cui-focus-ring-color)), so setting --cui-focus-ring-color or --cui-focus-ring-width at the root reaches every control, and a .theme-{color} region tints the rings inside it. Previously each component baked the resolved value in at build time, which is why a runtime change to the global ring left the components behind.

    - --cui-pagination-focus-ring: .25rem solid rgba(88, 86, 214, .25);
+ /* nothing to declare — the pagination link rings from the global tokens */

  • $input-btn-focus-color no longer reaches the input and control rings. They read the global ring now; set $focus-ring-color (or --cui-focus-ring-color) instead. $input-btn-focus-width is unaffected — it still sizes the validation rings and the button.

Sizes and colours are unchanged, so the ring keeps its width ($focus-ring-width, .25rem) and its translucent theme colour. What changes is the property drawing it, which also means the ring no longer participates in a box-shadow transition.

Each class writes var(--cui-radius-{n}) rather than the stop’s value, so a stop overridden on :root re-rounds the utilities along with the components. The side classes set logical corners (border-start-start-radius, …), so .rounded-top flips with the writing direction like .rounded-start already did.

  • Buttons and controls carry a line height per size. :root emits --cui-btn-input-xs-line-height (1.125), -sm-line-height (--cui-line-height-sm) and -lg-line-height (--cui-line-height-md), the size classes hand them to --cui-btn-line-height / --cui-control-line-height, and each size’s min-height is computed from its own line height. sm and lg keep the body value; the new .btn-xs is the only tighter size. --cui-border-width-keyline (.5px) is a root token now and .border-keyline reads it.

  • New .rounded-size-*. It writes the radius into --cui-rounded-size without setting border-radius itself, and the unprefixed side classes (.rounded-top, .rounded-end, .rounded-bottom, .rounded-start) read that token, so one size class drives whichever corners you round. With no size in scope they fall back to --cui-radius-5. A numbered .rounded-{n} writes the token as well, so .rounded-3 .rounded-top keeps the top on size 3; a side class with its own number (.rounded-top-3) sets that side directly.

  • The derived colour utilities compose with their opacity classes. .bg-*-subtle, .bg-*-muted, .border-*-subtle and .text-*-emphasis each wrote the property directly, so .bg-opacity-50 on a .bg-primary-subtle did nothing while the same class on .bg-primary worked. They now declare --cui-bg / --cui-border / --cui-text and resolve through the same color-mix() as the base families. Nothing changes at full opacity.
